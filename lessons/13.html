"While finding defects remains the main motivation for review, reviews are less about defects than expected." Bacchelli and Bird, Microsoft, 2013

Most people think code review exists to catch bugs. That's one of four jobs.

The second is keeping the code maintainable. The third is spreading knowledge, so more than one person understands each part of the system. The fourth is accountability. A second person put their name on it.

A well-known Microsoft study from 2013 found that reviews were less about defects than people expected. A lot of the value was knowledge transfer and better alternative solutions.

AI reviewers help mostly with the first job and somewhat with the second. They can explain a change to you, but the team still has to understand its own system, and a person still has to sign.

An AI reviewer is a language model, often several, prompted to find problems in a change. Before you pick a product, ask four things about it.

First, how much it reads. Some see only the diff. Some pull in surrounding files. Greptile builds a graph of the whole repository so it can judge how a change affects other code.

Second, whether it checks its own findings. Anthropic's managed Code Review runs several agents in parallel, then a verification step filters out false positives before anything is posted.

Third, whether it runs code. Anthropic's Code Review only reads. Other tools can run tests or drive a browser.

Fourth, how you steer it. The tools in this lesson each read a rules file from your repository.

Watch for the idea that a review bot is a special kind of system. It's the same kind of model you chat with, given a diff and a prompt to find problems.

Strengths and limits

AI reviewers are good at local bugs and weak at intent

They catch what's wrong inside the diff. They're poor judges of whether the change should exist, and they flag things that aren't problems.

Go deeper: what they are good and bad at

Good at

  • Local logic errorsoff-by-one, null handling, a missing await
  • Edge cases the tests skip
  • Code that doesn't match nearby code or the spec
  • Security smellsinjection, missing authorization checks, secrets in code
  • Another pass without getting tired
  • Speedminutes, where a person takes days

Weak at

  • Intentis this the right change for the product?
  • Architecturedoes it fit where the system is heading?
  • Effects outside the context it retrievedother services, downstream consumers
  • What the organization knowslast year's incident, a customer deal
  • Ranking cosmetic against critical, without tuning
  • Staying quiet

AI reviewers find local logic errors, such as an off-by-one, a null that isn't handled, or a missing await. They find edge cases your tests skipped. They spot code that doesn't match the code around it or the spec it was written from. They pick up common security smells. They also don't get tired, so a second pass costs minutes.

They're weak at judging whether this is the right change for the product, or whether it fits where the system is heading. They only know the context they retrieved, so effects on another service are easy for them to miss. They don't know about last year's incident.

Without tuning, a bot ranks a naming nit next to a data-loss bug. It also comments when there's nothing wrong.

Layer one is the author agent checking its own work before it asks anyone. Then CI runs the full test suite and the security scanners.

Layer two is an independent bot with a fresh context. Its findings don't go straight to a fix. Each one gets verified first. Confirmed findings go back to the author agent, and the fix goes through CI again. Findings that are refuted or not worth the trouble get a note and are dismissed.

Layer one costs you one prompt. It asks for two things.

The first is proof. Run the full test suite, the linter and the type checker, and show the output. You want the output on the page, because "all tests pass" is a claim and the log is the evidence. Lesson 11 called this proof of done.

The second is a coverage walk. The agent goes through the spec line by line and names the file and the test for each requirement. Anything without a test gets flagged.

In the example reply, two requirements have code and a test. The refund email has code and no test, and the agent says so. You now know where to look before any reviewer has spent a minute on it.

This layer is cheap, and it's the same model checking itself, so it shares the author's blind spots. That's why there's a layer two.

Layer 3

These are the questions the bots can't answer. The human doesn't need to find every null check again.

Design

By the time a change reaches a person, the tests have passed and a bot has been through the diff. The person's time is expensive, so spend it on three questions.

On intent, a change can be flawless and still solve the wrong problem. Only someone who knows the product can say.

On design, the bot sees one diff. You know where the system is going next quarter.

On risk, think about who notices if this is wrong in production, how fast, and how you'd roll it back.

You don't have to hunt for every null check again. The earlier layers are better placed for that, and they don't get tired. One risk is automation bias, which Lesson 11 covered. People tend to relax once a tool has passed something. Nobody has measured that for review bots yet, but a green bot review tells you nothing about these three questions.

Verify findings

Every bot finding is a hypothesis until you reproduce it

AI critics hallucinate bugs. And a reviewer asked to find problems "will always find something", so fixing every finding bloats the code.

Ask for a failing test before any fix.

Go deeper: verify findings before acting

The reviewer says: "<finding>". Don't fix it yet. First, write a test that demonstrates the failure, run it, and show me it fails. If you can't reproduce it, trace the relevant path and report REFUTED (with evidence) or UNRESOLVED (with the missing evidence). Failure to reproduce alone is not a refutation.

Confirmed

The test fails the way the finding said. Fix it.

Refuted

The traced path shows it can't happen. Dismiss it, with the evidence.

Unresolved

No failing test and no proof either way. Say what evidence is missing.

A bot's finding is a guess about your code. Sometimes the guess is wrong. OpenAI trained critic models to review code and found they caught more bugs than paid human reviewers. They also hallucinated bugs that could mislead people.

There's a second problem. Anthropic's docs warn that a reviewer asked to find problems will always find something. Fix everything it says and you end up with extra abstraction layers and tests for cases that can't happen.

So before fixing anything, have the agent write a test that shows the failure, run it, and show that it fails. Lesson 12's verifier did the same job in a fresh context.

Confirmed means the test fails the way the finding predicted. Refuted means the agent traced the path and has evidence it can't happen. Unresolved means it couldn't reproduce the bug and couldn't rule it out. A test that didn't fail doesn't prove the code is fine.

Watch for "the bot said it, so fix it." Have someone bring a bot comment from a real PR and try to reproduce it live.

Once a finding is confirmed, you still have to decide what to do with it. Settle that as a team before the bot posts its first comment. Otherwise every pull request turns into an argument about whether a comment has to be addressed.

High means real damage, such as lost data or a security hole. It blocks the merge until it's fixed and the fix is verified. Medium gets fixed in this pull request, or gets a ticket that has an owner. Low is the author's call.

Noise is style the formatter already handles, and vague comments that start with "consider". Don't triage those one at a time. Change the bot's settings so it stops sending them.

Give the room three sample bot comments and have them vote on a level for each. Disagreement here is the point of the exercise.

Six comments from a bot on one pull request. Five are nits. The fourth says a delete endpoint has no authorization check. By the time a tired engineer gets to it, they've already decided this bot isn't worth reading.

That's false-positive fatigue. The field studies of review bots agree on it. Noise is the main complaint, and precision decides whether people keep using the tool.

Raise the severity threshold. Codex on GitHub only reports its top two priority levels, and Claude's code review command at low effort reports only what it's most confident in. Write down what you don't want in the rules file. Give feedback, since some tools learn from how your team responds.

One detail about rules files is a security question. Find out which branch your reviewer reads them from.

A pull request has a base branch, usually main, and a head branch, which holds the proposed changes. Anthropic's Code Review reads its rules file from the base branch, and its docs say never from the pull request's own changes. GitHub's docs say Copilot reads its instructions from the head branch.

The right panel shows why that's a problem. The pull request adds two lines to the rules file telling the reviewer to skip the auth folder because security already approved it. If the reviewer reads rules from the head branch, it follows them. The change under review rewrote the rules it's reviewed against.

That's prompt injection, and the same text could sit in a code comment or a commit message. Nobody has good numbers yet on how well reviewers resist it. For now, know which of your instruction sources a pull request can change, and have a person look at any change to those files. Lesson 14 is all about this.

Reviewing AI-written PRs

AI-written code fails in recognizable ways

It's usually tidy, well commented and plausible, which makes the problems easy to skim past. Read the description and git diff --stat first to see whether the PR does what was asked and nothing else.

Go deeper: how humans should review AI-written PRs

  • Hallucinated APIsDoes every unfamiliar function, flag and config key exist in the version you use?
  • New dependenciesIs each package real, spelled right, maintained, needed and license-compatible?
  • Tests that test nothingAssertions on mocks, tests never seen failing, tests deleted, skipped or loosened
  • Swallowed errorsEmpty catch blocks, except Exception: pass, a silent empty return
  • Needless abstractionAn interface with one implementation, a factory for one class
  • Dead codeUnused functions, debug output, a helper that duplicates an existing one
  • SecurityAuthorization on every new endpoint, input validation, injection, secrets in code or logs
  • LicensingLarge blocks that look copied from somewhere

Code from an agent looks clean, which makes it easy to approve without reading.

Start with scope. Read the description and the list of changed files before any code. If the task was a bug fix and twelve files changed, ask why.

Then the checklist. Check that unfamiliar functions and flags exist in the version you run. Check every new package. Models invent package names, and attackers register those names with malicious code in them.

Look hard at the tests. Assertions against a mock, tests nobody ever saw fail, and tests that were quietly deleted or loosened are all common. Look for errors that get caught and thrown away.

Look for structure nobody asked for, such as an interface with one implementation. Look for leftovers like debug output and duplicate helpers. Check security on every new endpoint. Lesson 14 has the numbers on how often generated code is vulnerable.

Reviewing AI-written PRs

Learn to spot swallowed errors and tests that can't fail

Both look like careful code. One hides failures from the caller. The other raises your test count without checking anything.

Go deeper: how humans should review AI-written PRs

Swallowed error

def get_orders(user_id):
    try:
        return db.query("SELECT * FROM orders WHERE user_id = %s", user_id)
    except Exception:
        return []

The caller can't tell "no orders" from "database down".

Tautological test

it("fetches the user", async () => {
  const api = { getUser: jest.fn().mockResolvedValue({ id: 1 }) };
  const user = await api.getUser(1);
  expect(user).toEqual({ id: 1 });
});

It checks the mock against itself. No real code runs.

Two patterns from that checklist are worth learning to see at a glance.

The first is the swallowed error from the start of this lesson. The function queries the database for a user's orders. If anything goes wrong, it catches the exception and returns an empty list. The caller gets an empty list when the user has no orders, and the same empty list when the database is down. A customer sees "you have no orders" during an outage, and nothing shows up in your error tracker.

The second is a tautological test. It builds a fake API that returns an object with ID one. It calls the fake. Then it asserts that the result has ID one. None of your code ran. The test can never fail, and it still adds one to your count of passing tests.

When you see a test, ask what change to the real code would make it fail. If there isn't one, it tests nothing. Lesson 11's mutation check finds these. Break a line of the real code and see whether any test fails.

Ask the room: what change to the production code would make the second example fail? Answer: none. Then have them rewrite it so one would.

The person who opens a pull request is its author, whoever typed the code. If they can't explain a line, it doesn't merge.

A template helps enforce that. It asks what changed and why, which commands verified it and what came back, and what could break and how to revert.

It also asks the author to be straight about what the agent did and what they did. "The agent wrote the implementation and tests. I wrote the spec, reviewed every line and rewrote the retry logic." That tells the reviewer where to look hardest.

As a reviewer, ask questions the author has to answer in their own words. Why this approach rather than another. What happens when this input is empty. One answer should stop a review. "The agent did it that way" means nobody on the team understands the change yet.

Watch for people treating this as a rule against using agents. The rule is about understanding. The author can ask the agent to explain, then check that explanation against the code.

Review latency tells you whether review is the bottleneck, and whether a bot helped or just added a step. Pull request sizes predict review quality. Escaped defects are bugs found after merge, and they're the outcome review exists to prevent. Change failure rate is a DORA stability measure, and revert rate tracks much the same thing. The share of bot comments acted on tells you if the bot is useful. The share of pull requests with a substantive human review guards against rubber-stamping, where a person approves without really reading.

Don't target lines of code. It rewards bloat. Anthropic itself calls it an imperfect measure that counts quantity over quality. Pull requests merged is easy to inflate. Percentage of code written by AI describes adoption. Make it a target and people accept more AI output to hit it.

Goodhart's law applies to all of these. When a measure becomes a target, it stops being a good measure. Use them to spot trouble.

Faster

"Resolved" and "led to a code change" are different measures. A comment can be resolved without any change.

Two industrial studies got opposite results on speed.

On the left, a company added a bot built on the open-source PR-Agent. About 74 percent of its comments were marked resolved. The average time to close a pull request went up, from five hours 52 minutes to eight hours 20 minutes. Developers reported a small quality gain, along with faulty reviews and irrelevant comments.

On the right, Atlassian studied its own reviewer for a year. About 39 percent of comments led to a code change. Cycle time fell by about 31 percent, and people wrote about a third fewer review comments themselves.

Both bots found real issues. Whether one speeds a team up depends on its design and the context. A third study of 16 review tools found that short comments containing code were more likely to get acted on.

These studies count comments and time. Almost none measure whether fewer bugs reached production.

Ask what might explain one team getting slower and another getting faster. Then point them at the exercise in the full notes: plant five known bugs in a PR and score two reviewers on it.

What to remember

Three things to keep

  • The author agent checks its work, an independent bot reviews with a fresh context, and a human reviews intent, design and risk.
  • Reproduce a finding before you fix it, and tune the bot until people read its comments.
  • A named human approves every merge and owns the result.

Full notes

Keep three things from this lesson. First, stack the layers. The author agent checks its own work against the spec. An independent bot reviews with a fresh context, from a different lab if you can. Then a person reviews intent, design and risk.

Second, treat findings as guesses. Reproduce one before you fix it, and keep tuning the bot until people actually read what it says.

Third, a named human approves every merge and owns the result.

Have each person name one layer their team is missing and what they'd do this week to add it.
