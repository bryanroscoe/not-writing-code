AI coding tools started as autocomplete, then chat. Today's tools are coding agents. An agent reads your codebase, runs commands, writes and tests a change, and opens a pull request for you to review.

Author's noteVibe coding means you're not really ever reading the code. We're talking about AI-accelerated coding here.

Andrej Karpathy coined "vibe coding" in a post in February 2025. He was a founding member of OpenAI and ran AI at Tesla. You describe what you want, accept whatever the model writes, paste errors back in, and never read the diff.

That works for a prototype or a personal tool. It's a bad way to build software other people depend on.

This course teaches AI-accelerated coding. The AI does a lot of the typing. You read the code, test it, and answer for what ships. Simon Willison drew that line in March 2025. By early 2026 he reported that "agentic engineering" was winning as the name for the disciplined version.

People now say vibe coding for any coding with AI. In this course it keeps Karpathy's meaning, which is that nobody reads the code.

Ask when not reading the code is the right call. Prototypes and throwaway scripts are good answers.

The modes differ in who writes the code and who reads it. With hand-coding, you write and read everything. In a fully autonomous pipeline, agents write the code and other agents read it. Whether that last mode can be trusted is still contested, and lesson 10 covers the argument.

Most of this course covers supervised agents. The agent edits your repository and you review every diff. That mode fits most professional work today.

Parallel supervised agents means several agents on separate tasks. You still review, and the agents review each other. It suits experienced users who have good tests.

Background agents work unattended and open a pull request for you to review. They do well on tasks that are well specified and well tested.

This course keeps a human in charge, for three reasons that hold even as agents get better.

A model can't be fired, sued, or paged at three in the morning. Whoever merges the change owns it. In a class that means academic integrity. At work it means being on call. It also covers licensing, security and privacy.

In a 2025 trial by METR, an independent evaluator, experienced developers took 19 percent longer with AI tools while believing the tools had sped them up. METR now calls that result out of date. Its February 2026 follow-up estimates modest speedups with wide error bars. Neither study shows a gain that holds for everyone.

Studies of students and new developers find that letting AI do the work can reduce what you learn, even when the output is better. If you're a student, the skill you build is the point of the assignment.

Watch for "the tools will soon be good enough that nobody needs to review." Accountability stays with the person who merges, whatever the tool can do.

Six ideas run through the whole course. Every lesson builds on at least one of them.

A language model predicts the next token. Chat, reasoning and coding agents are all built on that, and the model has no built-in sense of what's true. Context is its working memory. Most of the skill in using agents is controlling what goes into it.

You can hand the checking to tests, builds and other agents. The responsibility stays with you. An agent is a model plus a harness, which is the program wrapped around the model. The same model scores very differently in different harnesses.

Anything the model reads can give it orders. A README, a web page or a tool result can carry instructions, and the model can't reliably tell data from commands. That is prompt injection, and it isn't solved. Cost follows the context processed and the output generated, and agents often resend the whole conversation on every turn.

Ground rules

Every exercise assumes six habits

They're also a decent starting policy for a team.

Go deeper: ground rules

  1. You own what you ship"The AI wrote it" is never an excuse, in a class or in a postmortem.
  2. Read every diff you mergeOr have a check you trust read it for you.
  3. Keep secrets and private data outNo credentials or other people's data in a tool your organization hasn't approved for that data.
  4. Disclose AI useWhere your course, employer or open-source project asks you to.
  5. A human approves anything irreversibleDeploying, deleting, sending, paying, force-pushing.
  6. When a tool surprises you, write it downThat log is the start of your own evaluation set.

Every exercise in the course assumes these six habits. They also work as a starting policy for a team.

You own what you ship, in a class or in a postmortem. Read every diff you merge, or have a check you trust read it. Start by reading everything, and read less once you've built tests and review you trust.

Keep secrets, credentials and other people's private data out of any tool your organization hasn't approved for that data. Disclose AI use where your course, your employer or an open-source project asks you to.

Keep a human approval step before anything you can't undo, such as deploying, deleting, sending, paying or force-pushing. And when a tool surprises you, write it down. A short log of "the model did this when I expected that" is the start of your own evaluation set.

Ask which of the six the room's teams already have written down.
