Harnesses, tools, and MCP

Lesson 08 · 22 min

Full notes

agent=model+harness

Stage three is about working with agents. This lesson covers the software wrapped around the model, called the harness. You will see what the harness sends to the model, what a tool call looks like, and what comes back.

After that come MCP, the standard for plugging tools into a harness, and the features most harnesses now share.

What a harness is

A harness is everything around the model

A model takes text in and predicts text out. It can't open a file, run a test or remember yesterday's conversation.

The harness is the software that turns that predictor into something that edits your codebase.

Agent = model + harness

A model alone takes text in and predicts text out. Everything else an agent does comes from the program around it. That program is the harness.

The dashed box on screen is the harness, with the model inside it. It has five parts. The agent loop calls the model again and again. Tools are functions the model may ask for, such as reading a file or running a shell command. Permissions decide which of those requests run on their own, which need your approval, and which are refused.

Context management decides what the model sees on each call. The user interface is how you watch and steer.

Claude Code, Codex and Cursor are all harnesses. An agent is a model plus a harness.

Ask the room to name the harness they use most. Then ask which model is inside it. Many people can't answer the second question.

The agent loop

The agent loop is a few lines of code

Call the model. If it asks for a tool, run the tool and put the result in the context. Call the model again. Stop when it replies without asking for a tool.

Most agents are a variant of this pattern, called ReAct: reason, act, observe.

while True:
    reply = model(context)  # reason

        context.append(result)  # observe
Illustrative

The loop at the center of every coding agent is short. Follow the diagram. Your task goes into the context window. The context goes to the model. The model replies with a tool call. The harness runs that tool if the permission rules allow it. The result goes back into the context, and the model is called again.

The code under the diagram is the same thing as about ten lines of Python. It's a sketch, but real harnesses are built around a loop like it. A call the rules refuse still gets a result. The model is told it was denied. The loop ends when the model replies without asking for a tool. That reply is the answer, the diff or the pull request.

The pattern has a name, ReAct, from a 2022 paper. Reason, act, observe. The rest of the harness makes this loop safer, cheaper or easier to steer.

Watch for the idea that the agent is a different kind of AI from the chat model. It is the same model called in a loop.

What the harness sends

Every model call carries the tool list

The harness sends the model a list of tool definitions. Each has a name, a plain-English description and a JSON Schema for its inputs.

Unless the harness loads tools lazily, that whole list goes along with every call.

The model was never given the tool's code. It only has these descriptions. And unless the harness loads tools lazily, the full list is sent again on every call, so each tool you add takes up context on every turn.

Ask how the model knows a tool exists. Answer: only from this list. Nothing about your tools is in its weights.

A tool call

A tool call is text, and the harness does the running

When the model wants to act, it outputs a structured tool call. The harness checks permissions, runs the function and puts the result back into the context.

The model's next step is based on that result.

A full run

One task is many trips around the loop

A small fix takes several calls: run the tests, read the file, edit it, run the tests again.

Each result lands in the context window, and the model reads all of it again on the next call.

Harness effects

The same model behaves differently in different harnesses

People say "model X is bad at Y" when the cause is the harness: its tools, its system prompt and defaults, how it manages context.

Evaluate coding models in the harness you'll use.

The model picks tools by their names and descriptions. A vague description produces wrong choices.

MCP

MCP turns a thousand integrations into a hundred and ten

Before MCP, ten harnesses and a hundred services meant a thousand custom integrations. With a shared protocol it's ten clients plus a hundred servers.

MCP, the Model Context Protocol, is an open standard for how an AI application discovers and calls outside tools and data.

Go deeper: MCP

Nov 2024Anthropic releases MCP
2025OpenAI, Google and Microsoft adopt it
Dec 2025Donated to the Linux Foundation's Agentic AI Foundation
Jul 2026The spec goes stateless

MCP stands for Model Context Protocol. It solves a counting problem.

The left sketch is the world before it. Three harnesses and four services need twelve custom integrations, one for every pair. At real scale, ten harnesses times a hundred services is a thousand.

The right sketch puts one protocol in the middle. Each harness speaks it once and each service speaks it once. Three plus four is seven. Ten plus a hundred is a hundred and ten. Anthropic's own comparison is a USB-C port for AI applications.

The timeline underneath shows how fast it spread. Anthropic released it in November 2024. OpenAI, Google and Microsoft adopted it during 2025. That December it moved to a Linux Foundation body, so no single vendor owns it. In July 2026 the spec dropped sessions, which lets a hosted server sit behind an ordinary load balancer.

Ask what else in software solved an N-times-M problem this way. The Language Server Protocol for editors is the usual answer.

MCP

A host talks to each MCP server through a client

The host is the AI app you use. It runs one client per server. A server is a program that exposes capabilities, such as GitHub or a browser.

Local servers run as a subprocess over stdio. Remote servers use Streamable HTTP, usually with OAuth.

MCP

To the model, an MCP tool is one more tool

An MCP server is a small adapter. It says "here are my tools and their schemas", then executes calls and returns results.

The harness turns those tools into entries in the model's tool list.

Below it is what the model ends up with. The harness asks the server what it offers. Then it adds an entry to the tool list from earlier in this lesson. The function name becomes the tool name. The model can't tell an MCP tool from a built-in one. It writes the same kind of tool call. The harness sees that the tool belongs to a server and forwards the call. Servers can also offer resources, which are data the app can read, and prompts, which are reusable templates. Tools are the part you'll use most.

MCP costs

Connected tools cost context before you type

Without lazy discovery, every connected server's tool definitions load into the context. Large tool lists also make tool selection less accurate.

Two fixes: tool search, which fetches definitions on demand, and code execution, where the model writes code that calls the tools in a sandbox.

MCP's first cost is context. Unless the harness loads tools lazily, every connected server puts all of its tool definitions into the context, and they are there on every call.

The top two bars are numbers Anthropic published in November 2025. In its example, five servers with 58 tools took about 55 thousand tokens before the conversation started. Inside Anthropic they had seen 134 thousand. A long tool list also makes the model worse at picking the right tool.

The bottom two bars show one fix, called code execution or code mode. The model writes a short program that calls the tools inside a sandbox. Intermediate data stays in the sandbox and never passes through the model. In Anthropic's example, one workflow dropped from 150 thousand tokens to 2 thousand.

The other fix is tool search. The harness loads one small search tool and fetches definitions only when they are needed. Until your harness does one of these, disconnect the servers you aren't using this week.

MCP, CLI or code

For your own agent, try the CLI first

There are three ways to give an agent a capability. Many engineers find an agent with shell access does better with gh, psql or kubectl than with an MCP wrapper of the same service.

The model knows those CLIs from training, and their output can be filtered before it reaches the context.

MCP security

An MCP server is code you run with your credentials

A malicious or compromised server can lie in its tool descriptions, change behavior after you approve it, or send your data out.

Any server that reads untrusted content, such as web pages, issues or email, is a prompt-injection channel.

The toolkit

The major harnesses share one toolkit

By 2026 the major harnesses had converged on the same features. The names differ a little between products.

Features are cheap to copy, so what you learn in one tool carries over to the next.

These ideas spread between products within months, because good features are easy to copy. The next three screens go deeper on skills, hooks and permissions.

Skills

Skills load their instructions only when needed

A skill is a folder with a SKILL.md and optional scripts. The agent sees a one-line description of every skill and reads the full instructions only when a task calls for them.

That's called progressive disclosure. You can keep dozens of procedures available without paying for them in every prompt.

Permissions

People approve 93% of permission prompts

Approval prompts sound safe, but people stop reading them. That's approval fatigue.

Use allowlists so the prompts that remain are worth reading. For long unattended runs, use a real sandbox with limited credentials.

Anthropic, March 2026. It calls auto mode "not a drop-in replacement for careful human review on high-stakes infrastructure."

Every harness has a setting for how much the agent may do without asking you. The row across the top shows the usual presets. At one end the agent only plans. At the other, nothing asks at all.

Asking every time sounds like the safe choice. In March 2026 Anthropic reported that users approve 93 percent of permission prompts. By the fortieth prompt you click yes without reading, so the prompt protects very little.

Anthropic's answer is auto mode. A second model, a classifier, approves routine actions and blocks risky ones. Anthropic was open about its limits. In their tests the full pipeline still missed 17 percent of overeager actions.

So for long unattended runs, use a real sandbox. That means a container, a virtual machine or a cloud environment, with limited credentials. Turn on the sandbox before you turn off approvals. And avoid bypass mode on your own machine.

Ask the room: is a prompt you always approve a safety feature? What would you replace it with?

Closed products

Closed products hide the harness from you

Some products bundle a model, a harness and tools into one experience. They're often the fastest way to get a specific job done.

The vendor can change the model, prompts or limits at any time. For a workflow your team depends on, prefer tools whose configuration you can see and version.

Some products hide the harness completely. The vendor chose the model, the loop, the tools and the interface, and you get one sealed box. The chips name a few: a design canvas, a browser extension that clicks for you, cloud agents that return pull requests.

These are often the fastest way to get one job done. Two cautions apply to all of them.

First, they change underneath you. The vendor can swap the model or the prompts any day. That's fine for a prototype. For a workflow your team depends on, prefer a tool whose configuration you can read and keep in version control.

Second, browser and computer-use agents are the riskiest kind. They read untrusted web pages while holding your logged-in sessions. The bars are Anthropic's own numbers from its Chrome launch. Without mitigations, injection attacks worked about 24 percent of the time. With them, about 11 percent. Read lesson 14 before you point one at your email.

A demo video is a poor basis for choosing a harness. The grid has eight questions to ask instead.

Start with model access. Some harnesses lock you to one vendor's models, and others let you bring any model. Then cost. Agent work burns a lot of tokens, so flat subscription versus per-token billing is a big difference. Lesson 15 covers that. Then privacy: where your code and prompts go, and how long they are kept.

You protect yourself with portable formats. Put team knowledge in AGENTS.md, in skills and in MCP servers. Most harnesses read those, so switching later is cheap.

Go deeper: a sane baseline setup

Keep three things from this lesson. First, an agent is a model plus a harness. The harness calls the model, runs the tool the model asks for, puts the result back in the context, and repeats. When results get worse, check the harness as well as the model.

Second, everything you connect has a price. Tool definitions take context, and a server runs with your credentials. Connect the one to three servers you need, and try a command-line tool first.

Third, an instruction file is a request and a hook is a rule. Put what must always happen in hooks. And turn on a sandbox before you turn off approvals.

Have each person pick one change to their own setup: one server to disconnect, one hook to add, or one skill to write.
