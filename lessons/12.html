Why use more than one

Extra agents buy four things, and a smarter answer isn't one of them

A subagent is usually the same model as the one that spawned it, or a smaller one, working on the same task.

Go deeper: why use more than one agent

  • ParallelismIndependent pieces finish sooner. It saves wall-clock time.
  • Context isolationA subagent can read 200 files or a full test log and hand back one paragraph.
  • Different perspectivesA security-focused reviewer finds problems a correctness-focused one skips.
  • Independent verificationA reviewer that never saw the author's reasoning isn't swayed by it.

"You get parallelism or a fresh pair of eyes out of it, but not a smarter answer."Claude Code best practices, Anthropic

Pieces that don't depend on each other finish sooner when agents run in parallel. You save time on the clock, and the answer is no smarter for it.

A helper can read two hundred files or a full test log and hand back one paragraph. That keeps the noise out of your main conversation.

A reviewer told to look only at security finds problems that a correctness reviewer skips. And a reviewer that never saw the author's reasoning can't be talked into it. Anthropic's docs list that as a main reason to use subagents.

The same docs add the caution quoted here. A subagent is the same model, or a smaller one, on the same task. Expect speed and fresh eyes from it.

The first cost is tokens. Anthropic measured its own systems in 2025. A single agent used about four times the tokens of a chat. Its multi-agent research system used about fifteen times.

In the same write-up, token usage alone explained 80 percent of the variance in performance on a benchmark called BrowseComp. So a good share of what looks like teamwork is the system spending more compute on the problem.

That changes how you judge a multi-agent setup. Compare it with one agent given the same token budget, and see whether the arrangement adds anything on top. Lesson 15 covers what those tokens cost on a subscription and on an API.

Ask the room: a system scores better and uses fifteen times the tokens. How would you tell better design from more compute? Answer: give a single agent the same budget and compare.

The second cost is lost context. When an agent hands work to a subagent, it writes a brief. The brief is a summary. The subagent doesn't get the conversation that led to it.

Walden Yan at Cognition wrote a post in 2025 called "Don't Build Multi-Agents". His example is on screen. Split "build a Flappy Bird clone" between two subagents. One builds a background that looks like Super Mario. The other builds a bird that doesn't match the game. Neither saw the conversation behind its brief, so each filled the gaps its own way. A final agent is left to reconcile two halves that don't fit.

Yan's two principles follow from that. Share full context and full agent traces, beyond individual messages. And remember that every action carries decisions nobody wrote down. When two agents make those decisions separately, the decisions conflict.

Ask what the two briefs left out. Answer: the art style, how the bird should move, everything the lead agent assumed and never wrote down.

Why not

A central check catches some errors before they spread

A controlled study of 260 agent configurations estimated from execution traces how much each design amplifies errors, with a single agent as the baseline.

A separate analysis of more than 1,600 traces from seven frameworks sorts the failures into 14 modes. One group of them is missing or wrong verification.

Go deeper: why not

Trace-level error amplification, single agent = 1×

Independent agents, no central check17.2×
Centralized, with a verification step4.4×

Kim et al., "Towards a Science of Scaling Agent Systems", 2025, revised April 2026.

The last two costs are coordination breaking down and errors compounding.

The bars come from a controlled study by researchers at Google and MIT. They ran 260 agent configurations with the tools, prompts and compute held constant. The measure is what the paper calls trace-level error amplification. It's estimated from execution traces, and a single agent is the baseline at one.

Independent agents with no central check came out at about 17. A centralized design, where an orchestrator checks the work before combining it, came out at about 4. The check cut the amplification to roughly a quarter. Final error rates moved far less. They were about 1.1 to 1.3 times a single agent's.

A second study looked at more than 1,600 traces from seven multi-agent frameworks and sorted the failures into 14 modes. Agents ignore each other's input. They stop before the task is done. A whole group of the failures is verification that's missing, incomplete or wrong.

Ask where the verification step sits in a multi-agent setup someone in the room has used. If nobody can point to it, that's the finding.

The read/write asymmetry

Reading parallelizes, and writing usually doesn't

Research, review and verification produce claims. You can deduplicate claims, check them and throw away the wrong ones.

Every edit carries decisions about names, data shapes and error handling. Decisions made separately don't fit together, and the edits collide in git.

Read-heavy work parallelizes well. Write-heavy work on one codebase usually doesn't.

Research, code review, verification and debugging with competing hypotheses are read-heavy. Each agent produces claims. "Line 42 can divide by zero." "The bug is in the cache layer." Claims combine easily. Two reviewers flagged the same line, so you merge them. One claim turned out wrong, so you drop it. Two reviewers who disagree cost you a minute of checking.

Writing is different, because every edit carries decisions. Take two writers on the same module. One names the field with an underscore, the other uses camel case. One raises on error, the other returns None. Neither is wrong alone. Put together they give you a broken build and a merge conflict.

Ten reviewers can work at once. Ten writers on one module make ten sets of decisions.

Ask for a writing task that does parallelize well, and what makes it different. Hold the answers for two screens.

Parallel writing can work. The work has to be made independent first.

In early 2026 Anthropic published a project where 16 agents built a C compiler in parallel. For most of the project that went well. A big test suite produces many separate failures. Each agent claims a different one, so they rarely touch the same code.

Then they tried to compile the Linux kernel. The kernel is one giant test. Every agent hit the same first bug, fixed it, and overwrote the others' changes.

The fix was a harness that compiled most kernel files with GCC, a known-good compiler, and only the rest with the new one. A failure then pointed at a small set of files. Each agent could chase a different bug again.

The engineering effort went into splitting the work. Adding agents was the easy part.

Go back to the question from two screens ago. A writing task parallelizes when something outside the agents, such as a test suite, has already cut it into separate pieces.

Most multi-agent setups are built from seven patterns. You don't need to memorize the table. Use it to name what a tool is doing and to know its trap.

An orchestrator with workers splits a task while it runs. That suits open-ended research, and it fails when the briefs are vague. Fan-out then merge runs fixed slices in parallel, one per directory or per concern. Budget for the merge, because that's where conflicts show up.

Voting and best-of-N run the same task several times and keep the majority or the best. A generator and critic loop produces, critiques and revises. A critic always finds something, so cap the rounds. Debate gets its own screen next. A judge panel has several models score the same output. A pipeline is fixed stages, such as locate, fix, validate.

In 2024 a fixed three-stage pipeline called Agentless scored 32 percent on SWE-bench Lite, the best of any open-source agent at the time, at 70 cents an issue. Try the plain design first.

Name a tool the room uses and ask which pattern it is. Code review bots are usually fan-out then merge.

Patterns

Most of debate's gain comes from the vote

A 2025 study split multi-agent debate into its two parts and found that majority voting alone accounts for most of the improvement.

Another found that debate can lower accuracy over rounds, because models switch from correct to incorrect answers to agree with their peers.

Illustrative

Debate sounds like the smartest pattern. Agents argue over several rounds and converge on an answer. The 2023 papers that introduced it for language models reported gains.

Later work took it apart. A 2025 paper called "Debate or Vote" separated the two ingredients. It found that majority voting alone accounts for most of the gains credited to debate. In a plain vote, three agents answer on their own, two are right, and the majority is right.

Talking adds a risk. Another 2025 paper found debate can lower accuracy over rounds. Models shift from correct to incorrect answers in response to a peer's reasoning. They favor agreement over challenging a flawed argument. In the example, agent 2 gives in and the majority flips to the wrong answer. Lesson 01 called this sycophancy, and here it happens between agents.

So the baseline to beat is several independent attempts and a vote, or a test.

The team exercise in the full notes tests this directly. Ten checkable questions, three conditions: one agent, three with a vote, three with a debate.

Review swarm

A review swarm splits by concern, then tries to refute each finding

Reviewers stay read-only, and their findings are checked before anyone edits. Shipping review tools have the same shape.

This pattern is called a review swarm. The work is read-heavy, the reviewers are independent, and there's a verification step in the middle.

You freeze a target, so everyone reviews the same commit. You fan out to several reviewers, one per concern. The five on screen are correctness, security, tests, compatibility and simplicity. Several of them will flag the same line, so you merge findings by location and root cause.

Then, for each finding, a fresh agent tries to prove it wrong. Confirmed findings get ranked by severity and go to a person. Refuted ones are dropped. No reviewer edits anything.

Commercial tools do the same. As of November 2026, Anthropic's managed Code Review runs several agents over the diff and the surrounding code in parallel. A verification step then filters out false positives, and what's left is ranked by severity.

The individual exercise is this diagram by hand with three reviewers. Fresh sessions, one concern each, on a pull request of 50 to 300 lines.

Freeze the target first. Review a specific commit or diff, since a branch keeps moving.

Go deeper: shared or isolated context

  • The diff at one commit SHA

Every reviewer gets the same three things. The diff at one specific commit. The spec or the issue. And read-only access to the repository, so it can look at the surrounding code and can't change it. In Claude Code, a custom agent limited to Read, Grep and Glob can't edit.

You hold back the author's conversation. It contains the author's reasoning, and a reviewer that reads it gets anchored by it.

This looks like it contradicts the Flappy Bird screen, where the advice was to share full context. The two cases differ. Builders need shared context so their decisions fit together. A reviewer's value comes from being independent of the author. Where exactly that line sits is still an open question in the field.

Freezing the target is the other half. If the branch moves while five reviewers are reading, their findings point at lines that no longer exist.

Ask the room: Cognition says share full context, and good review says withhold the author's reasoning. How do both hold? Answer: share the artifacts, meaning spec and code. Withhold the argument for why the code is right.

Review swarm

Give each reviewer one concern and permission to find nothing

A required failure scenario makes each finding checkable.

A reviewer asked to find problems will always find something, so the brief says that an empty report is acceptable.

Go deeper: a review swarm

Reviewer brief

You are reviewing a change you did not write. Focus only on SECURITY. Inputs: the diff (git diff main...HEAD), SPEC.md, and read-only repo access. For each finding give: file:line, a concrete failure scenario (specific input or state -> wrong behavior), and severity (high/medium/low). Report only issues that would cause real harm. Skip style. If you find nothing, say so. Do not invent findings to seem useful.

Repeat for correctness, tests, compatibility and simplicity.

This is a reviewer brief you can paste.

"You did not write" sets the reviewer up as an outsider. "Focus only on security" gives it one concern. A reviewer with one concern goes deeper than a reviewer told to look at everything. You run the same brief again with correctness, tests and so on.

"A concrete failure scenario" is the phrase that makes the next step possible. The reviewer has to name a specific input or state and the wrong behavior that follows. A finding in that form can be tested. "This looks risky" can't.

The last highlight is "if you find nothing, say so". A model asked to find problems will produce some, real or imagined. Telling it that an empty report is fine removes the pressure to pad. So does "skip style", which keeps forty comments about naming out of your list.

Live demo. Run this brief on a small diff twice, once with the last line and once without it. Count the findings each time.

Go deeper: a review swarm

Verifier brief

A reviewer claims: "<finding>". Your job is to check whether it is real. Trace the code path. If possible, write a test that demonstrates the failure and run it. Answer CONFIRMED (with evidence), UNRESOLVED (can't prove either way, say what evidence is missing), or REFUTED (explain why the scenario can't happen).
CONFIRMEDGoes in the report, with the evidence
UNRESOLVEDReported only if it's high severity
REFUTEDDropped

The verifier is the step most home-made review setups skip. Each finding goes to a fresh agent, and that agent's job is to check whether the finding is real.

The verifier traces the code path. If it can, it writes a test that shows the failure and runs it. A failing test is evidence from outside the model, which Lesson 11 showed is the kind that holds up.

It answers with one of three verdicts. Confirmed, with evidence. Unresolved, when it can't prove it either way. Refuted, with the reason the scenario can't happen. You report the confirmed ones, and the unresolved ones only if they're high severity. The person at the end gets a short ranked list.

The research behind this is OpenAI's CriticGPT work from 2024. AI critics caught many bugs and also invented some. Teams of a human and a critic hallucinated less than the critic alone.

If the verifier refutes most of one reviewer's findings, that reviewer is noise. Change its prompt or drop it.

Ask why the verifier should be a fresh agent and not the reviewer itself. Answer: the reviewer already believes its finding.

Cross-model review

A model reviewing its own code is primed to like it

Models can recognize their own writing, and the better they recognize it, the more they prefer it. Judges also score familiar-looking text higher, whoever wrote it.

So review in a fresh context at minimum, and with a different lab's model when it counts.

Panickssery et al., 2024, on self-recognition and self-preference. Wataoka et al., 2024, on familiarity. Verga et al., 2024, on panels from different model families.

Language models tend to rate their own output higher.

Two 2024 papers explain it. One found that models can tell their own writing from other models' writing, and the stronger that self-recognition, the stronger the preference for their own text. The other traced the bias to familiarity. A judge scores text higher when the text looks predictable to that judge, whoever wrote it. Code a model just wrote looks very familiar to that model.

Never ask the session that wrote the code whether the code is good. A fresh context with the same model is the minimum. A different lab's model is better. Panels drawn from different model families showed less of this bias in evaluation studies. Whether that carries over to code review is a fair guess that hasn't been shown yet.

Keep the reviewer strong. A much weaker one gives you confident noise. And verify across models too. If one model finds a bug, have another try to refute it.

Ask what this implies for a team that uses one vendor for everything. Their author and reviewer share blind spots, so a fresh context is the floor.

Parallel builders

To build in parallel, write the interfaces first

This fits a large migration, a greenfield project with clear modules, or a backlog of independent chores.

For one hard task, consider best-of-N. Two or three agents do the same task in separate worktrees and you keep the best. It costs N× and there's nothing to merge.

Sometimes you do want several agents writing at once. A big migration, a new project with clear modules, or a pile of unrelated chores can all justify it. The recipe makes that work independent before you start.

The interfaces go in first. Types, API contracts and function signatures live in a shared file, created by one change that a person reviews. Those are the decisions that would otherwise be made three different ways.

Then split by module. Each agent gets its own worktree, its own branch and its own failing tests. That's the compiler lesson again. Separate failures make separate work.

Then merge one branch at a time. Rebase, run the full suite, merge, repeat. Steve Yegge's Gas Town orchestrator has a dedicated agent for this step, because otherwise parallel workers fight over rebases.

There's an alternative for one hard task, called best-of-N. Run two or three agents on the same task in separate worktrees and keep the best result. You pay several times over, and there's nothing to merge.

Don't loop review and fix forever. A reviewer asked for problems always finds something. Fixing all of it leads to extra abstraction layers and tests for cases that can't happen.

Anti-patterns

Five setups that add tokens without adding a check

Go deeper: anti-patterns

Org-chart theater

A "CEO agent", a "CTO agent" and a "QA agent" all see the same information and have no tests to run.

Debate without a referee

Agents talk until they agree. Agreement isn't correctness, so give the debate an external check or a vote.

The telephone game

A summarizes for B, B summarizes for C, and detail evaporates at each hop. Pass the original artifacts.

Self-review as the only review

One model in one context, grading itself.

Unbounded fan-out

"Use as many agents as you need", with no cap.

Org-chart theater gives agents job titles. A CEO agent, a CTO agent and a QA agent all read the same information and none of them has a test to run. The early papers that built software teams this way mostly tested small, self-contained programs. They aren't evidence that role-play beats one strong agent on a real codebase.

Debate without a referee is agents talking until they agree. The debate screen showed why agreement isn't correctness. The telephone game is summaries of summaries. Pass the original diff, spec and logs down the chain.

Self-review as the only review is one model in one context grading itself. And unbounded fan-out is the prompt that says "use as many agents as you need."

Give the system a limit and a check from outside the agent that did the work.

Ask which of the five the room has seen in a demo or a product pitch.

What to remember

Three things to keep

  • Run reviewers in parallel freely. Run writers in parallel only after the work has been made independent.
  • Verification is what stops errors spreading. Have a fresh agent try to refute each finding.
  • Never let the session that wrote the code be its only reviewer. Use a different lab's model when it counts.

Go deeper: what the evidence adds up to

Reading parallelizes and writing mostly doesn't. Run writers side by side only after interfaces and tests have cut the work into separate pieces.

The verification step is the part that pays, and a model is primed to like its own code. So a fresh agent tries to refute each finding, and a different lab's model reviews when the change is important.

The research shows gains from multi-agent setups shrinking as single models improve. When you upgrade models, test again whether your extra agents still earn their tokens.
