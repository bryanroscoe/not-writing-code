Verifiers and oracles

A verifier checks the work against an oracle

A verifier is a test, tool or separate model that checks an agent's claimed result. The oracle is the source of truth it checks against, often an expected value a person wrote into a test.

Verifiers differ in how far you can trust them. A type checker gives the same answer every time. A model judge can be swayed by how the code looks.

Two terms for the rest of the lesson. A verifier is whatever checks the agent's claim. A compiler is a verifier. So is a test suite, a linter, a screenshot comparison, or a second model asked whether the work is right.

The oracle is where the right answer comes from. In the test on screen, the highlighted string is the oracle. A person decided that "Hello, World!" should become "hello-world" and wrote it down. An oracle can also be a second implementation, a rule that must hold for every input, or a saved output you know is good.

Prefer verifiers that give the same answer every time. Use a model as the verifier only where nothing else fits.

The ladder of checks

The agent can climb most of the ladder itself

The low rungs are fast and cheap and catch narrow kinds of mistakes. The high rungs are slower and catch more of what a user would notice.

A good setup lets the agent climb as far as it can before a person looks. A type checker catches a hallucinated API before any test runs.

Read the ladder from the bottom. Types and lint run in seconds. They catch methods that don't exist, wrong argument types and typos. That includes the invented APIs from Lesson 01. Then come unit tests for one function, and property tests for edge cases nobody wrote down.

Higher up, integration tests check your assumptions about a real database or another service. The agent can usually run those if it can start the services, often with Docker. Simon Willison's line is that passing tests doesn't mean the code works as intended. He has agents exercise their code directly. The top rung is a person, who judges intent, design and risk. No agent runs that one.

Outside feedback

"Review your work" is the weakest feedback you can give

Prompted models fix their mistakes when the feedback comes from outside: test results, compiler errors, a different reviewer. Without it they sometimes make things worse.

A failing test with its error message carries information the model didn't already have.

The obvious shortcut is to tell the model to check itself. The research says that mostly doesn't work. Three results are on screen.

First, Huang and colleagues had GPT-3.5 review its own answers on a commonsense benchmark, with no outside signal. Accuracy fell from about 76 percent to about 38 after one round. The model was more likely to change a right answer to a wrong one.

Second, Reflexion, an agent that reflects on its failures. The test was the 50 hardest HumanEval problems, translated to Rust. With tests it writes and runs, it scored 68 percent. Take the test running away and it scored 52, below the 60 percent GPT-4 got with no reflection at all.

Third, GPT-4 repairing code. Its own feedback fixed a third of the failing programs. Feedback from a human fixed more than half.

All three studies are from 2023, on GPT-3.5 and GPT-4. In each case the gain came from a signal the model didn't produce itself. A related finding: generating several candidates and keeping one that passes the tests works. Generating one and asking the model whether it's right mostly doesn't.

Watch for "newer models fixed this." A 2024 survey found fine-tuning can enable self-correction. Nobody knows yet whether that gets self-checks to the point where you'd skip the test.

Some things have no test: readability, whether a design fits, whether a doc is accurate. A model judge helps there, and its verdict is weaker evidence than an executable test.

Models got good at code partly because training rewarded them for passing checks. The same training left a habit of satisfying a check in ways nobody intended.

Tests as the contract

Write the test first and watch it fail

Test-driven development means writing a failing test before the code that makes it pass. It suits agents because the loop has something to converge on.

Write or approve the tests yourself, commit them separately, and make each one fail first. A test that never failed may not test anything.

Oracles

Find the oracle before you hand a problem to a loop

The problems agents loop on best have clear success criteria. Before you start a loop, find or build what it will check against.

"The code is good" isn't a check. If you can't name the command that proves the task worked, run the task by hand until you can.

Simon Willison's advice for agent loops is to look for problems with clear success criteria. The table lists five kinds of oracle and how each one goes wrong.

A failing test suits bug fixes and small features. A golden output is a saved result you know is right, good for refactors and report generators. The easy cheat there is regenerating the snapshot, so treat a changed snapshot like a changed test. A reference implementation is a second program that must agree with yours. Anthropic's agent-built C compiler was checked against GCC that way. A reference answers for every input, including ones you never thought to write down.

A property is a rule that holds for every input. The next screen shows one. Tests the model writes itself can rank candidate solutions, but they need their own check. In the Reflexion paper, the self-written tests had a 16 percent false-positive rate on one benchmark.

Most product work has no oracle, because the spec lives in people's heads. Write the spec down as checks first, or keep a person in each iteration.

Ask each person to name the oracle for the task they're working on this week. "I'd know it when I see it" doesn't count.

Property tests

A property test makes up inputs the agent hasn't seen

You state a rule and a tool hunts for counterexamples. Hypothesis tries 100 random inputs by default and reports the simplest one that fails.

An agent can't hard-code answers for inputs that are made up fresh on every run. Weak properties can still pass, though.

Go deeper: property-based tests

from hypothesis import given, strategies as st
from slug import slugify

@given(st.text())
def test_slugify_is_idempotent(s):
    assert slugify(slugify(s)) == slugify(s)

@given(st.text(), st.integers(min_value=1, max_value=80))
def test_slugify_respects_max_length(s, n):
    assert len(slugify(s, max_length=n)) <= n

Passes both

def slugify(s, max_length=80):
    return ""

A normal test checks the inputs you thought of. A property test states a rule and lets a tool look for an input that breaks it. The tool here is Hypothesis, for Python. By default it tries 100 random inputs, including edge cases you may not have considered. When one fails, it reports the simplest failing input it can find.

The code states two rules for a slug function. Running it twice gives the same result as running it once. And the result is never longer than the maximum length you asked for.

This blocks the hard-coding trick from earlier, because the inputs are new on every run. It has its own hole, shown at the bottom. A slug function that always returns an empty string passes both rules. These two properties were too weak to fail it.

Models can help write properties, unevenly. In a 2023 study, GPT-4 wrote a correct property test for only 21 percent of the properties found in API documentation.

Loops

A loop is only worth building with a checkable end state

A loop replaces you as the person who types "continue". It needs an independent check, a budget, and state kept outside the conversation.

It also needs isolation, such as a worktree, and a rule to stop and ask before anything irreversible. A loop's "done" is still a claim, so a person reads the diff before it ships.

A loop takes over the job of typing "continue". Follow the diagram. The agent reads a state file, such as a plan or a checklist, and does one item. A verifier checks it. That's tests, a linter, or a model that didn't write the code. A failure goes back to the agent. A pass gets written to the state file and committed.

Then the loop asks whether the goal or the budget has been reached. A budget is a cap in turns, time or tokens. If not, it reads the state again. If so, it stops and reports to a person.

The one-line script under the diagram is the simplest version, the Ralph loop, from Geoffrey Huntley in July 2025. The same prompt file runs forever, with a fresh session each pass and all memory in files. Huntley wires in tests and a type checker to reject bad output. He also says you'll sometimes wake up to a codebase that doesn't compile, and that he'd never use it in an existing codebase.

Protecting the verifier

The defenses are mechanical

Watching the model's reasoning isn't a reliable defense. When OpenAI researchers put a chain-of-thought monitor into the training reward, agents learned to hide their intent (Baker et al., 2025).

Start with the cheapest one. A deny rule or hook on the tests folder applies every time, whatever the model decides.

If instructions and monitoring aren't dependable, the defenses have to be mechanical. Lesson 04 drew the boundary: tests the agent can't change and checks it never sees. The list runs roughly from least effort to most.

Make the tests read-only while the agent implements. A deny rule or a hook that blocks edits to the tests folder applies every time. Read the full test diff, as you saw earlier. Keep holdouts, which are grading tests the agent never sees, and run them yourself after it says it's done. StrongDM's team keeps its end-to-end scenarios outside the codebase for this reason.

Holdouts need care. If they sit in a folder the agent can read, they stay hidden only while the agent follows instructions. In June 2026 METR reported GPT-5.6 Sol packaging exploits to reveal a hidden test suite. Keep holdouts outside the agent's sandbox and run them from a separate step.

The last three. Prefer property and differential tests, which generate inputs the agent hasn't seen. Test your tests, which is the next screen. And have a fresh context review the work, ideally a model from a different lab.

Mutation testing

Break one line by hand to test your tests

Coverage records which code ran. It doesn't tell you whether the tests can detect a fault.

Mutation testing breaks the code on purpose, one small change at a time, and reruns the tests. If they all still pass, the mutant survived and a test is probably missing.

Coverage tells you which lines ran during the tests. It doesn't tell you whether any test would fail if a line were wrong. Mutation testing answers that. You break the code on purpose in one small way and rerun the tests.

At the top, one line of the slug function is changed so the result can be one character too long. On the left, all 12 tests still pass. The mutant survived, so no test checks the length limit. On the right, one test is added, and the same broken line now fails it.

Tools such as Stryker and PIT automate this and report a mutation score. You don't need a tool to start. Break a line by hand and run the tests. A survivor is a strong hint and falls short of proof, since some changes don't alter behavior at all.

This is also how you catch a tautological test, one that checks the code against itself. Every mutant survives it.

Calibrating trust

A green check can make you review less carefully

That's automation bias. It affects novices and experts alike, and training or instructions don't prevent it, so the fix has to be in the process.

Scale the evidence to the risk of the change, however confident the agent sounds.

Developers say they're wary. In Stack Overflow's 2025 survey, 46 percent actively distrusted the accuracy of AI tools. Saying so doesn't mean checking carefully, though. Lesson 08 had Anthropic's number from March 2026. Users approve 93 percent of permission prompts.

So put the care into the process. A copy change needs a glance. A change to payments, auth, data deletion or a migration needs the full proof of done, a review in a fresh context and a second person. Read a sample of passing work too, since cheating shows up in runs that passed.

Checking has a cost as well. Aim for the cheapest check that catches the mistakes you actually see, and add a rung when something gets through.

This one is opinion, and it's labeled that way. The author likes loops and goals, with a limit: the goal can't be too ambitious or the agent goes off the rails. Loops with a hard, checkable goal and a person reading the result work. Open-ended loops that run unattended and ship to production don't, yet.

The strongest case against that view is a project with a near-perfect verifier. Nicholas Carlini's C compiler project at Anthropic had GCC to compare against and decades of conformance tests. Parallel agents built it mostly unattended. His lesson was that the task verifier has to be nearly perfect, or the agent will solve the wrong problem.

Most product work has no oracle like that. You have to build its checks and protect them.

What to remember

Three things to keep

  • An agent stops when the model thinks it's done. Give it a check it can run that returns pass or fail.
  • Agents game the check. Keep tests out of their reach, read the test diff, and hold some tests back.
  • "Done" is a claim. Ask for the commands and their output, then rerun one yourself.

Go deeper: try it

Keep three things from this lesson. First, an agent stops when the model thinks it's done. Give it a check it can run itself, one that returns pass or fail.

Second, agents game whatever check you give them. Keep the tests out of their reach, read the test diff, and hold some tests back.

Third, "done" is a claim. Ask for the commands and their output, and rerun one yourself.
