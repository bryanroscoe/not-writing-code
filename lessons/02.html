The pipeline

A model is made in stages

Pretraining reads a broad sweep of text and produces a base model. Post-training turns that base model into an assistant and a reasoner.

Real pipelines are messier than this picture. Stages repeat, overlap and run in different orders at different labs.

A model is built in stages, and each stage is more training on different data.

The top row is pretraining. The network predicts the next token across trillions of tokens. Near the end comes a loosely named phase called mid-training. The data gets better and more specialized, the sequences get longer, and the learning rate comes down. The learning rate is how far each training step moves the weights. What comes out is a base model. It completes documents, and it doesn't yet follow instructions reliably.

The middle row is post-training: example conversations, feedback on better and worse answers, then rounds of reinforcement learning on tasks a program can check. Lesson 01 called the first of those instruction tuning. Lesson 03 covers the whole row.

The bottom row is what happens after release. Open weights can be fine-tuned, and big models get distilled into smaller ones. Treat the whole diagram as a mental model. Recent open recipes run several reinforcement learning stages in different orders.

Pretraining data

Pretraining data is the web, filtered hard

Most of it comes from web crawls such as Common Crawl. Duplicates, spam and boilerplate come out, classifiers score quality, and some personal data gets stripped.

Labs add code, books, papers, math and many languages, plus a growing share of synthetic data written by other models.

The raw material for pretraining is mostly the public web. Common Crawl is a free archive of crawled pages, and many datasets start there.

Follow the funnel down. Duplicate pages come out, along with spam and navigation boilerplate. Filters keep the pages that are in the right language and pass quality checks. Some personal data is stripped. Hugging Face documented this whole process in an open project called FineWeb, and it ended with about 15 trillion tokens.

The chips underneath are what labs add on top: code from public repositories, books, papers, math, other languages. More and more of it is synthetic, meaning another model wrote it.

This explains a pattern from lesson 01. A model is strong on what the web has a lot of, and weak on your private codebase, which it never saw. The data is also contested. There are copyright lawsuits and consent debates over it. Lesson 18 covers a related question, the copyright status of the code a model writes.

Ask what is over-represented on the public web, and what is missing. Then ask how that shows up in the code a model writes.

Hardware

A model is mostly matrix multiplication, so it runs on GPUs

A transformer layer multiplies token vectors by large weight matrices, over and over. A CPU has a few dozen powerful cores built for branchy code. A GPU has thousands of simpler cores plus dedicated matrix-multiply units.

Google's TPUs, AWS's Trainium and AMD's Instinct chips make the same bet. Together they're called accelerators.

TFLOPS: trillions of floating-point operations per second. NVIDIA's headline 1,979 assumes sparse matrices. The dense figure is 989.

Lesson 01 described what a transformer layer does. Under the hood, nearly all of that work is one operation: multiplying vectors by very large matrices of weights.

A CPU is the wrong tool for it. A CPU has a few dozen powerful cores designed for code full of branches. A GPU has thousands of simpler cores, and it adds units that do nothing except multiply matrices. NVIDIA calls those Tensor Cores.

The two bars are the same chip, an NVIDIA H100. On general math it does about 67 trillion operations a second. On matrix math it does 989 trillion. That is roughly fifteen times more, on the one operation a model needs.

Google, Amazon and AMD build their own chips on the same idea. The shared name is accelerators. One caution when you read a spec sheet. NVIDIA's headline numbers usually assume a trick called sparsity that doubles them, so halve the number before you compare.

Pull up one accelerator's spec page and find the dense 16-bit figure together.

Compute

Training costs about 6 FLOPs per parameter per token

A FLOP is one floating-point multiply or add. Running a token forward through the network costs about 2 per parameter. Training adds a backward pass that costs about twice as much again.

So the compute for a whole training run is roughly 6 × parameters × tokens.

Go deeper: FLOPs

one multiply, one add

Backward pass: 4
works out how to adjust each weight

6 × N × D

N: parameters in the model
D: tokens it trains on

Inference only runs the forward pass, so generating or reading a token costs about 2 FLOPs per parameter.

You can estimate the compute for any training run with one rule.

The unit is the FLOP, one floating-point multiply or add. To push one token forward through the network, each parameter costs about two of them: one multiply and one add. Those are the two dark blocks.

Training has a second half. After the forward pass, the network works backward to find how each weight should change. That backward pass costs about twice the forward pass, so four more blocks. Six in total.

Multiply that by the number of parameters and by the number of training tokens, and you have the whole run. People write it as six N D. The rule comes from a 2020 paper on scaling laws.

Using a model only runs the forward pass.

Have the room estimate before the next screen. 405 billion parameters, 15.6 trillion tokens, times six. Just the exponent will do.

Interconnect

One model is trained across thousands of chips that talk constantly

The training state for Llama 3 405B is about 6.5 TB, more than 80 times one H100's memory. So the work is split across chips, over two tiers of wiring.

Scale-up links such as NVIDIA's NVLink join a small group of chips tightly. Scale-out is the datacenter network between groups, and it carries much less per chip.

One chip can't train a frontier model. It would take thousands of years, and the model doesn't fit. Training keeps about 16 bytes of state for every parameter. For 405 billion parameters that is about 6.5 terabytes, and one H100 holds 80 gigabytes.

So the work is split, and the chips have to talk to each other the whole time. The diagram shows the two kinds of wiring. Inside a server, eight GPUs share a link called NVLink. Each GPU gets 1.8 terabytes per second. Between servers, the whole box shares 1.6 terabytes per second of ordinary network. Per GPU that is about nine times less.

That gap decides how the software is laid out. The bottom row is how Meta split Llama 3. The split that needs the most communication cuts each weight matrix across the eight GPUs in one server, so it stays on the fast link. The layers are cut into sixteen groups along a pipeline. Then up to 128 copies of that pipeline each take a different slice of the data.

The names for these are tensor, pipeline and data parallelism.

Ask why you can't just buy more servers and connect them with ordinary networking. Answer: the split that talks the most would be waiting on the slow link.

The memory wall

Writing one token rereads every weight

When a model generates for one user, each weight is fetched from memory, used once and dropped. The math finishes almost instantly and the chip waits for the next fetch.

Chips have gained compute much faster than memory bandwidth. That widening gap is called the memory wall.

Training is limited by how much math the chips can do. Generating text is limited by something else, and it explains why a model writes more slowly than it reads.

Take a small model, Llama 3 8B, writing for one user on one H100. Its weights take 16 gigabytes. To produce one token, the chip has to read all 16 gigabytes from its memory. The top bar is that read: about 4.8 milliseconds.

The bottom bar is the math for the same token. It takes 16 microseconds. You can barely see it. The chip spends more than 99 percent of each token waiting on memory.

The two tiles turn that into speed. Memory limits this setup to about 210 tokens a second. If math were the limit it would be about 60,000.

The chips at the bottom show why this keeps getting worse. Every two years compute has grown about three times, and memory bandwidth only about 1.6 times. People call that gap the memory wall. Lesson 06 uses the same sum to estimate speed on a laptop.

Ask the room to guess which is the bottleneck before you reveal the bars. Most people guess math.

The memory wall

Batching shares one read of the weights across many users

Serve many users at once and each weight fetched gets used once per user. On an H100 it takes a batch of roughly 300 before decoding stops waiting on memory.

Each user's KV cache, the saved attention state for their conversation, is separate, so those reads aren't shared.

The fix for the memory wall is to share the read.

On the left, one user. The chip reads every weight and does one user's math with it. One square.

On the right, 300 users at once. The chip still reads every weight once per step. Now it does 300 users' math with each one. Three hundred squares from the same read.

The line underneath gives the break-even for an H100. Divide its peak math by its memory bandwidth and you get about 295 operations for every byte it reads. So you need a batch of roughly 300 before the math units are the limit. Newer chips land between about 210 and 310, so a batch in the low hundreds is still the target.

One thing isn't shared. Each conversation has its own saved attention state, called the KV cache, and it has to be read separately. That is why serving at scale is mostly a batching and memory-management problem.

The memory wall

Training is limited by compute, generation by memory speed

Training runs huge batches, so every weight a chip fetches gets reused across many tokens and the math units stay busy.

Inference has two phases. Prefill reads your whole prompt at once and behaves like training. Decode writes one token per step and waits on memory.

Training, on the left, is compute-bound. Llama 3 405B trained on 16 million tokens per step. Every weight a chip fetches gets used on many tokens, so the math units stay busy. Meta got 38 to 43 percent of the chips' peak math into the model itself. That is the 400 out of 989 from the worked example. Training's memory problem is space. Inference, on the right, has two phases. Prefill is the model reading your prompt. All the tokens go through together, so it is fast per token. Decode is the model writing, one token per step, waiting on memory each time.

You see this every day. A long prompt is read in a moment and the answer trickles out. One research system served up to 7.4 times more requests by putting the two phases on separate GPUs, and chip vendors have started designing separate chips for the two jobs. Google announced a training chip and an inference chip in April 2026.

Ask why an agent that reads ten files and writes a two-line fix feels fast, and one that writes a 500-line file feels slow.

Low precision

Fewer bits per weight means less memory and faster tokens

Storing each number in fewer bits helps three ways. Weights take less memory, each token moves fewer bytes, and chips do more low-precision math per second.

Quantization does this to a finished model. It costs some quality, so re-run your evaluation afterward.

Each weight is stored with some number of bits. The chart is an 8 billion parameter model at three sizes. At 16 bits the weights take about 16 gigabytes. That is the usual format for training and for released weights. At 8 bits they take about 8 gigabytes, and quality is usually close. At 4 bits they take about 4.5 to 5 gigabytes, often with a small loss.

Shrinking a finished model this way is called quantization. It is how open models fit on a laptop. If you download a file in the GGUF format, the label on it tells you how many bits it uses.

The loss is uneven. It shows more in small models, and it shows more on code and math, which is our use case. So after you quantize, run your own evaluation again.

Labs use the same idea at full scale. DeepSeek-V3 was trained mostly in 8 bits. OpenAI's open model gpt-oss stores most of its weights in 4 bits so that 120 billion parameters fit on a single 80 gigabyte GPU.

Ask why a 4-bit model would hurt code more than chat. One wrong character breaks a program. A slightly odd word doesn't break a sentence.

Distillation

Distillation trains a small model to imitate a big one

The big model is the teacher and the small one is the student. Inside a lab, a big model often teaches its smaller siblings this way.

Hinton, Vinyals and Dean showed in 2015 that the teacher's full probability distribution carries more information than the single right answer.

Distillation

Distilling from text alone works through any API

There are three flavors. They differ in what passes between teacher and student.

Output distillation needs only the teacher's text, which is why closed labs worry about it. The other two need the teacher's token probabilities.

Go deeper: distillation

Logit distillation

Teacher→ token probabilities →Student

Text alone isn't enough for this one, so it mostly happens inside a lab.

Output distillation

Teacher→ lots of written answers →Student

The student is fine-tuned on the text. Works through any API that returns text.

Stanford Alpaca, March 2023: 52,000 examples generated with an OpenAI model, under $600 in total.

On-policy distillation

Student→ its own answers →Teacher→ a grade for every token →Student

The student learns from its own mistakes instead of copying the teacher's text. The grade comes from the teacher's token probabilities.

About a tenth of reinforcement learning's GPU-hours in the Qwen3 team's comparison: 1,800 against 17,920.

With language models there are three ways to distill, and each row shows what passes between teacher and student.

In the first, the student sees the teacher's probabilities for every token. That is the richest signal, like the cat and lynx example. It needs access that outsiders don't get, so it mostly happens inside one lab.

In the second, the student only sees text. You ask the teacher a huge number of questions, save the answers and fine-tune the student on them. This works through any API. In 2023 a Stanford team did it for under 600 dollars, using 52,000 examples from an OpenAI model. They restricted it to research, partly because OpenAI's terms forbid building competing models that way.

The third is newer. The student writes its own answers and the teacher grades every token, which again takes the teacher's probabilities. The student is corrected on its own mistakes. In the Qwen3 team's comparison it needed about a tenth of the GPU-hours of reinforcement learning and scored higher. Recent open models use it between training stages so that earlier skills aren't forgotten.

Ask which of the three a company with only API access could run. Answer: output distillation only. Then ask what the API provider could do about it.

Distillation

Closed labs accuse rivals of distilling through their APIs

The major closed labs' terms prohibit using their outputs to build competing models. Distilling a strong model works, so labs now defend against it, and the defenses sometimes affect legitimate users.

Synthetic data

Training on model output degrades a model unless real data stays in

Train each generation only on the previous generation's outputs and quality drops. Rare information vanishes first, then outputs converge on bland averages. This is called model collapse.

In follow-up experiments, keeping the real data alongside the synthetic data avoided it.

Illustrative

Models now write a lot of the data that trains other models. That raises an obvious worry about a loop feeding on itself.

The left panel is the worry, and it is real. A 2024 paper in Nature trained each generation of a model only on the previous generation's output. Quality dropped. The curves show the spread of what the model can produce. Rare information, out in the tails, vanished first. Then everything converged on a bland middle. The name is model collapse.

The right panel is the follow-up. When researchers kept the original real data and added synthetic data to it, collapse didn't happen.

Labs do the second thing, with a filter. They generate math problems with checked answers, code with tests and reasoning traces, and they keep only what verifies. So collapse is a risk for careless loops, and it can be avoided.

Watch for "the internet is filling with AI text, so models will get worse." That depends on whether real data stays in and whether outputs are filtered.

What to remember

Three things to keep

  • Pretraining turns trillions of filtered tokens and months of GPU time into a base model.
  • Training is limited by compute. Generating text is limited by how fast a chip can read its weights.
  • Check a cost, power or distillation claim for what it counts and who is making it.

Go deeper: try it

Keep three things from this lesson. First, a base model is what you get when trillions of filtered tokens meet thousands of GPUs for months. You can estimate the size of that job with six N D.

Second, training and generation hit different limits. Training runs out of compute. Generation waits on memory, which is why a model writes more slowly than it reads, and why batching and smaller numbers help.

Third, read the big claims carefully. A training cost usually covers one run. A gigawatt figure may be a plan. A distillation charge comes from a party with a stake.
