Two kinds of open

Open-source software and open-weight models are separate choices

An open-weight model publishes its trained weights. Open-source software publishes a tool's code under a license that lets you read, modify and redistribute it. This lesson is about the software.

Either one can be paired with the closed version of the other.

Licenses

Read the license file before you depend on a tool

Most tools in this lesson use MIT or Apache-2.0. Both allow almost anything with attribution, and Apache-2.0 adds an explicit patent grant.

A source-available license such as the FSL lets you read and modify the code but forbids a competing commercial product. Some projects use different licenses for different parts.

Frameworks

A working agent loop is about 30 lines

Anthropic's "Building effective agents" warns that frameworks "often create extra layers of abstraction that can obscure the underlying prompts," and suggests starting with direct API calls.

This loop has one tool, a permission check, truncated tool output and a turn budget. It has no sandbox, so run it only in a disposable environment without real credentials.

def run(cmd: str) -> str:
    if input(f"run `{cmd}`? [y/N] ").strip() != "y":  # the permission system
        return "The user declined to run this command."
    p = subprocess.run(cmd, shell=True, capture_output=True, text=True, timeout=120)
    return (p.stdout + p.stderr)[-10_000:]  # crude context management

messages = [{"role": "user", "content": "Make the failing test in tests/ pass."}]
for turn in range(30):  # a budget, so it can't run forever
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        print("".join(b.text for b in resp.content if b.type == "text"))
        break
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": b.id, "content": run(b.input["cmd"])}
        for b in resp.content if b.type == "tool_use"
    ]})

Before you reach for an agent framework, look at how small an agent is. Anthropic's guide, Building effective agents, warns that frameworks often add layers of abstraction that hide the underlying prompts. It suggests starting with direct API calls.

The code on screen is most of a working agent. Start at the for loop. It sends the conversation to the model. If the model asks for a tool, the loop runs the command and appends the result. If the model answers in plain text, the loop prints it and stops.

The three highlights are the controls. The input prompt is the whole permission system. The slice that keeps the last ten thousand characters is the context management. The range of thirty is a turn budget, so it can't run forever.

Contributing to open source is one of the best ways for a student to learn real engineering. The ten steps on screen are a path through a first contribution.

The first panel happens before you write any code. Pick a project you use, because you'll understand its users and care about the result. Read the contributing guide and the AI policy. Then use AI to understand the code. Ask an agent to explain the architecture, trace a request, or explain why a test fails. That is the highest-value and lowest-risk use.

Say which issue you're taking before you start. Some projects forbid AI tools on good first issues. LLVM is one, because those issues exist to teach.

The second panel is the change. Reproduce the bug by hand and write a failing test. Write or heavily revise the fix yourself. If an agent drafts it, rework it until you could have written it, and delete what you can't defend. Then get a different model or a classmate to review the diff.

The third panel is the pull request. Write the description in your own words, disclose how you used AI, and answer review questions from your own understanding. Keep a log of what you learned. For a course, that log is the evidence of learning. The merged pull request is a bonus.

Ask what a student should do when a reviewer asks a question they can't answer. Answer: say so, then go find out.

What to remember

Three things to keep

  • "Open source" covers a stack of layers. An open harness can still drive a closed model.
  • Harnesses, MCP servers and skills are dependencies. Check the license, the maintainer and the governance before you install.
  • On someone else's project, understand every line, disclose your AI use and follow the project's policy.

Go deeper: try it

Keep three things from this lesson. First, open source in AI tooling is a stack of layers, and one open layer tells you nothing about the next. An open harness can drive a closed model.

Second, every harness, MCP server and skill you install is a dependency that runs with your agent's permissions. Check the license, the maintainer and who governs the project. Read it before you install it.

Third, when you contribute to someone else's project, understand every line, disclose your AI use, and follow the project's policy. Review time is what maintainers are short of.
