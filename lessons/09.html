Five "___ engineering" names, 2020 to 2026.

Lesson 01 called the context window the model's working memory. This lesson is about managing that memory once an agent is doing the work, and about the names the field keeps inventing for the job.

The five words on screen are those names, in the order they appeared. Each one covers more ground than the one above it.

The ladder

Each new name asks a wider question

From 2020 to 2026 the field climbed a ladder of "___ engineering" names. Each rung widens the scope: the words, the whole context window, the agent's environment, the repetition, then how several agents connect.

Some rungs name real techniques. Others rename older ones.

Between 2020 and 2026 the field went through five names for one kind of work. Each name took off from a specific post or essay, and each asks a wider question than the one before.

Read the rungs from the top. Prompt engineering asks what words you send. Context engineering asks what is in the window at each step. Harness engineering asks what the environment prevents, checks and corrects. Loop engineering asks what prompts the agent and when it stops. Graph engineering asks how many agents and steps connect.

The names age fast, and another rung will probably show up within months. The five questions should last longer, so the rest of this lesson takes them in order.

Prompt engineering

A good prompt gives the reason, the limits and a check

Prompt engineering is writing the instructions, examples and constraints you send to a model. Models now guess intent well, so most of the old tricks faded. A short list of basics has survived every upgrade.

Name the outcome, give the reason, define done, and give the agent a check it can run.

Some advice that helped older models now hurts. Anthropic keeps a list of it in the Claude Code docs, under the heading "What you can stop doing".

The first is shouting. Capital letters and the word "important" used to improve adherence. Anthropic's own April 2025 guide recommended them. The current docs say emphasis mostly makes the model over-apply the rule. A rule with no exceptions belongs in a hook, which the harness enforces.

Ask who still has capital-letter rules in a prompt or an instruction file, and whether they've tested them against a plain version.

Context engineering

In an agent, your prompt is the smallest part of the context

In a chat app the context is mostly your conversation. In a coding agent, your typed prompt is often the smallest part of what the model sees.

Context engineering is choosing everything that fills the window at each step. The name took off in June 2025.

Lesson 01 listed what sits in a context window. In a coding agent the proportions are lopsided. Read down the table. The harness adds a system prompt of thousands of tokens on every call. Tool definitions can run past fifty thousand tokens. Instruction files load at session start. Then the agent starts reading files and running tests, and those results are often the largest share. Your typed messages are the small row in the middle.

That gap is where the term "context engineering" came from. In June 2025 Shopify's CEO, Tobi Lütke, said he preferred it to "prompt engineering". He described it as "the art of providing all the context for the task to be plausibly solvable by the LLM." Andrej Karpathy agreed a few days later, and the name stuck.

Run /context once in a real session. Most people are surprised by how much is in the window before they've typed anything.

Context limits

Models use a long input unevenly

Windows grew from a few thousand tokens to a million. That doesn't mean a model uses every token equally well.

"Lost in the Middle" (2023) found models do best when the relevant fact sits at the start or end of the input. Later studies found performance dropping as the input grows, more so when it holds distracting material.

Illustrative curve

Lesson 01 ended its context screen with a warning that bigger isn't always better. This is the research behind it.

The curve is the shape from a 2023 paper called "Lost in the Middle". A model does best when the fact it needs is at the start or the end of the input. Bury the fact in the middle and accuracy drops.

You'll hear that frontier models now ace the needle in a haystack test, where one fact is hidden in filler. They do. That test is easy, and it says little about real work. The three rows under the curve are harder versions. In NoLiMa, the question and the fact share no keywords, and 11 of 13 models fell below half their short-input score at 32,000 tokens. Chroma's Context Rot study found all 18 models it tested getting worse as input grew.

For agent work, put the important instructions where they're easy to find and keep lookalike material out.

Watch for "it has a million-token window, so I'll paste everything." Ask what the distractors in that paste would be.

Context limits

You run out of focus before you run out of space

With million-token windows and automatic compaction, you rarely hit the limit anymore. Attention and cost are what limit you now.

Irrelevant material still dilutes the model's focus, and you pay for every token on every call. Prompt caching lowers the price and leaves the distraction.

Bryan's take

Context management is important. Once context gets stale, that's bad. Don't keep the same thread around for a long time. Models get dumber the larger the context gets and the longer a session has been going. Start fresh sessions often.

In 2026 the practical advice changed. Windows hold a million tokens and harnesses compact the history on their own, so running out of room is rare. Claude Code's docs now list aggressive window management as outdated advice.

The same docs still tell you to run /clear between tasks. Their reason is on the right: a focused context gets you better answers and costs less.

A context window works more like a desk than a filing cabinet. Everything on the desk competes for attention. A cluttered desk slows you down even when the right paper is somewhere in the pile. You also pay for every token on every call. Caching makes those tokens cheaper. The clutter stays.

The quote at the bottom is Bryan's opinion, labeled as his. He starts fresh sessions often, because a long thread goes stale.

The four moves

Four moves keep a context focused

In July 2025 LangChain sorted the techniques into four buckets: write, select, compress and isolate. Each maps to features you can use today.

Two mistakes come up a lot. One is preloading material "just in case". The other is running twenty tasks in one marathon session.

Go deeper: the four moves

Write

Save it outside the window so it survives.

progress files and plans in the repoissue trackersauto memorycommit messages

Select

Bring in only what's relevant, when it's relevant.

search with grep and globskillspath-scoped rulestool searchretrieval

Compress

Keep only the tokens you need.

compactiontrimmed tool outputfilters like jq and head

Isolate

Give separate work separate windows.

subagents with fresh contexta session per taskparallel agents in worktreesa fresh reviewer

Anthropic describes context as a finite resource with diminishing returns. The goal it sets is the smallest set of high-signal tokens that gets the job done. LangChain's four moves are the ways to get there.

Write means saving state outside the window, in a plan file or an issue tracker, so it survives a fresh session. Select means pulling material in when it's needed. An agent that can search with grep doesn't need the architecture doc pasted in up front. Compress covers compaction and trimming tool output. Isolate means separate windows for separate work. A subagent does a noisy search and hands back only the answer.

Two mistakes are common. The first is preloading: pasting whole documents, or connecting every MCP server you might need. The second is the marathon session. Twenty tasks in one conversation leave stale and contradictory context behind. Start fresh between unrelated tasks and keep the state in files.

Ask the room to sort their own habits into the four buckets. Most people find one bucket empty.

Harness engineering

Harness engineering turns each agent mistake into a permanent fix

In February 2026 Mitchell Hashimoto described a habit: any time the agent makes a mistake, engineer a solution so it never makes it again.

Six days later OpenAI's Codex team published a report under the same name. Underneath, it's developer-experience and CI work aimed at a new kind of user.

Lesson 08 covered what a harness is. Harness engineering is the habit of improving it every time the agent gets something wrong.

Mitchell Hashimoto, who co-founded HashiCorp, put it this way in February 2026. Any time the agent makes a mistake, take the time to engineer a solution so it never happens again. Sometimes the fix is one line in the instruction file. He says each line in his file is based on a bad agent behavior. Sometimes it's a script, like a screenshot tool or a test runner that filters its output.

Six days later OpenAI's Codex team reported on a product built this way. By their account, a handful of engineers drove Codex to about a million lines in five months with no hand-written code. They said one big instruction file didn't work. They replaced it with a file of about 100 lines that points into a docs folder, and they lint the docs to keep them honest.

That report comes from a company selling the tool, so read it as a claim.

Instruction files

Models follow instructions worse as the list grows

An always-loaded file competes with the task for the model's focus on every task, whether or not a given line applies.

A July 2025 benchmark called IFScale put up to 500 simple instructions into one task. Across 20 models accuracy fell as the count rose, and the best reached 68% at 500.

Go deeper: the fall

The paper also found a bias toward earlier instructions. Its task is synthetic: a report that must include up to 500 keywords.

Illustrative curve, real endpoint

The first problem with a long instruction file is attention. The whole file is in the context on every task. Claude Code's docs say longer files consume more context and reduce adherence.

There's a benchmark for this. IFScale gives a model one writing task and a growing list of simple instructions, up to 500 of them. The researchers ran 20 models. Accuracy fell as the list grew. The dot on the right is the best result at 500 instructions: 68 percent. They also found that models favor instructions near the top of the list.

Treat this as a warning sign. The task is synthetic, and a repository workflow is a different thing. The line between the two ends of the chart is drawn by hand. The endpoint is real.

If rule 300 in your file is the one you care about, test whether the agent follows it.

Watch for "the model has a million tokens, so 500 rules is nothing." Fitting in the window and being followed are different properties.

Instruction files

Context files raised cost without raising success

A 2026 study from ETH Zurich ran Claude Code, Codex and Qwen Code with and without context files. Success rates barely moved, and inference cost rose by more than 20%.

The agents did follow the instructions. Directory overviews still didn't help them find the right files any faster.

The second problem is that the files often didn't help. A team at ETH Zurich tested this in 2026 with three harnesses and four models, on two benchmarks.

The left panel is for files written by a model, the kind an init command generates. Task success went down slightly on both benchmarks, by amounts too small to tell from noise. Cost went up by 20 to 23 percent. The right panel is for files written by developers. Success went up 2.4 percent, also within the noise, and cost rose by as much as 19 percent.

The agents were reading the files. The line under the panels shows it. When a file mentioned a tool called uv, agents used it. Otherwise they almost never did. So instructions get followed, and the agent pays for following them with extra steps.

Generated files mostly repeated the README. They helped only in repositories with little other documentation. The authors recommend skipping generated files for now, keeping human-written ones minimal, and testing any file before you rely on it.

Instruction files

Most instructions have a better home than the instruction file

Skills, path-scoped rules and hooks took over most of what the big files did. A skill loads only its name and description until it's needed. A path-scoped rule loads when the agent touches matching files.

Rules with zero exceptions become hooks, deny rules or sandbox settings. Capital letters don't enforce anything.

The big files shrank because better places appeared for most of their contents. Lesson 08 introduced skills and hooks. Here they take work off the instruction file.

Read the table by row. A rule that must hold every time goes in a hook or a deny rule, where the harness enforces it. Claude Code's docs put it bluntly. If you keep adding emphasis to a line and the agent still misses it, that line belongs in a hook.

Style goes to the formatter and linter. A procedure you need once a month, like cutting a release, becomes a skill, so an unrelated bug fix never loads it. A rule for one part of the codebase becomes a path-scoped rule.

Anything the agent can discover by reading the code gets deleted. That covers the directory tree and the tech stack. The study on the last screen found architecture overviews didn't speed up file discovery, and agents with good search tools find what they need.

Loop engineering

A loop prompts the agent so you don't have to

A loop replaces you as the person who types "continue". Something else prompts the agent: a schedule, or a goal it keeps working toward.

The harnesses ship this now. Claude Code has /loop and /goal, and Codex has scheduled tasks and its own /goal (as of November 2026).

The next rung is about who does the prompting. In June 2026 Addy Osmani published an essay called "Loop Engineering". It quotes Peter Steinberger: "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

Follow the diagram. A trigger starts the agent. It can be a schedule or a goal. The agent works one turn. Then something independent checks the result, such as the tests or a second agent acting as verifier. If the goal isn't met, the loop saves its progress outside the conversation and runs again. When the goal is met or the budget is spent, it stops and a person reads what came out.

The idea is older than the name. In July 2025 Geoffrey Huntley described the Ralph loop, one shell loop that feeds the same prompt file to an agent over and over.

In Claude Code, /loop reruns a prompt on an interval. /goal keeps going until a condition holds, and a separate small model judges that condition after every turn.

Ask what in this diagram is new and what is cron plus a while-loop. Both answers are partly right.

Loop engineering

A loop needs an end state a program can check

A loop is only worth building when the task has a checkable end state, an independent check, a budget, and a human who reads the result.

Osmani's own warning: "done" from a loop is "a claim and not a proof". Lesson 11 covers verifiers and loop patterns.

Bryan's take

I like loop engineering and setting goals, but the goals can't be too ambitious or the agent goes off the rails. Loops with a hard, checkable goal and a human in the loop reading the result work for me. Open-ended loops that run unattended and ship to production don't, yet.

A loop will happily run forever on a task that has no finish line. So before you build one, check for four things. The task has an end state that either holds or doesn't. Something independent checks it. There's a budget that stops the loop anyway. And a person reads the result.

Osmani's essay carries its own warnings. A loop saying "done" is a claim and not a proof. He also warns about cognitive surrender, which means letting the automation do your thinking until you no longer understand the work.

The quote on screen is Bryan's opinion. Hard, checkable goals with a human reading the result work for him. Open-ended loops that ship to production unattended don't yet.

Others report going further. OpenAI's harness team says most of its review is agent-to-agent. Cursor reports a week-long multi-agent run that built a web browser. Those results rest on heavy investment in tests and verification, and they come from companies that sell the tools. Lesson 10 takes up how much autonomy holds up in practice.

Ask for one task from someone's backlog. Have the room decide whether it has a checkable end state, and what the check would be.

Graph engineering

Five workflow shapes cover most graphs

A graph here is a set of steps (nodes) joined by transitions (edges), with shared state. A loop is a graph whose path returns to an earlier node.

Anthropic described the common shapes in December 2024. Most coding work needs one or two of them at most.

Go deeper: graphs in practice

Prompt chaining

Plan, implement, write tests, summarize.

When the steps are fixed and each can be checked.

Routing

Triage issues to bug, docs or feature handlers.

When inputs fall into distinct classes.

Parallelization

Security, performance and correctness reviewers on one pull request.

When the work splits cleanly, or you want several attempts.

Orchestrator-workers

A lead agent splits a migration across modules, one worker per worktree.

When the subtasks aren't known in advance.

Evaluator-optimizer

Generate code, run a critic model and the tests, revise until both pass.

When you have a clear quality bar.

Each extra node is another place for errors to compound, and more tokens to pay for.

The top rung is about shape. A graph is a set of steps joined by transitions, with some shared state. A loop is the special case where the path comes back to an earlier step.

In December 2024 Anthropic published "Building effective agents". It separated workflows, where code decides the path, from agents, which direct their own process. It named the five workflow shapes on screen.

Chaining feeds one step's output to the next. Routing classifies the input and picks a path. Parallelization runs pieces at once, or runs one task several times and compares. Orchestrator-workers has a lead agent split the task and hand out the parts. Evaluator-optimizer has one model generate and another critique, in a cycle.

Most coding work needs one or two of these. Anthropic's 2024 advice still holds. Find the simplest solution possible, and add complexity only when you can measure the benefit. Lesson 12 covers what the research says about multi-agent systems.

Ask which shape the room's code review setup already is. Usually it's parallelization or evaluator-optimizer.

Graph engineering

The graph patterns are older than the name

The label took off from a Peter Steinberger post on X on July 18, 2026. The posts popularized the name. They don't establish who coined it.

The patterns were already in libraries and guides in 2024, and workflow engines are decades old.

The timeline shows how a name gets made. The first two rows are from 2024. LangChain shipped a library called LangGraph that wrote these graphs out in code. Anthropic published its guide to the five shapes that December.

Then nothing much happened to the name for a year and a half. On July 18, 2026, Peter Steinberger asked on X whether people were still talking loops or had shifted to graphs. Within hours Hamel Husain had posted an article declaring loop engineering dead. Courses and roadmaps appeared within days. By August there was a 35-author survey.

Turing Post traced the story. It read Steinberger's post as a playful question. It also checked a viral claim that graph engineering had replaced retrieval at Microsoft, Stanford and Anthropic. The claim was false. Its numbers came from one paper about engineering diagrams.

The work underneath is workflow orchestration. That work is real and useful, and it existed before the label did.

Ask the room what changed in practice between July 17 and July 19, 2026.

Substance or relabel

The measured claims held up and the viral ones mostly didn't

Context degradation, the value of verifiers and harness effects all have evidence behind them. "Graph engineering" mostly renames workflow orchestration that existed in 2024.

A new name often arrives with a new product feature, so ask what changed in practice.

The lasting skill is systems engineering around a component that behaves randomly. Each rung names one part of that work. The prompt is the input. Context is the working memory. The harness is the environment, the loop is the control flow, and the graph is the topology.

The right-hand column gives a verdict on each. Prompt, context and harness are mostly substance. Loop is partly substance and partly packaging. Graph is mostly a new name for older work.

None of the old layers went away. Prompts still sit inside a context. Context still has to be managed inside a loop. And every graph contains loops.

A new name often marks a new product feature. Loop engineering arrived as the harnesses shipped loop and goal commands. That gives vendors and course sellers something to sell. It doesn't make the idea wrong.

The measured claims have held up. The viral ones mostly haven't. The claim that graph engineering had replaced retrieval turned out to rest on one narrow paper.

Ask the room to argue which rung adds the most new substance. Push for evidence.

What to remember

Three things to keep

  • Your prompt is a small part of what an agent sees. Choose the rest on purpose, and start fresh sessions often.
  • Keep the instruction file short. Write only what the agent can't learn from the code, and move the rest to hooks, skills and scoped rules.
  • Build a loop or a graph only around an end state a program can check, and read the result yourself.
