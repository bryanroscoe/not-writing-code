Agentic workflows

Lesson 10 · 22 min

Full notes

This lesson is about working with a coding agent day to day. It covers the loop every agent runs, the workflow that holds up in practice, and how much autonomy to hand over.

The five words on screen are that workflow. By the end you will know what each step is for, and what the evidence says about agents that run with nobody watching.

The agent loop

An agent is a model in a loop

A chat assistant answers once and waits. An agent keeps going: it thinks, calls a tool, reads the result, and thinks again.

Lesson 08 showed this loop as code and named the pattern, ReAct. Every coding agent you'll use is a version of it with tools for files, shells and the web.

A chat assistant answers once and waits for you. An agent keeps going. It is a language model in a loop that can take actions and see what happened.

Follow the three boxes in the middle. The model thinks and decides the next step. It acts by calling a tool, such as reading a file, searching, editing or running the tests. Then it observes, which means the tool's output goes into its context. The line underneath runs back to the start, and it thinks again.

Lesson 08 showed this loop as code and gave it its name, ReAct, short for reason plus act. Claude Code, Codex, Cursor's agent and Copilot's agent mode are all versions of it.

Lesson 08 looked at the loop from the harness side. This lesson looks at it from your side: what you ask for, what you check, and how much you hand over.

Live demo. Give an agent a one-line task and have the room call out think, act or observe for each line of its log.

The key fact

The loop stops when the model thinks it's done

The agent stops when the work looks done to the model. Without a check it can run, you become the test suite.

Give it a check that returns pass or fail: a test, a build, a linter, a screenshot. Then ask for the evidence.

What you control

You control four things, whatever the tool

What the agent knows, what it can do, how it knows it's done, and how long it may run.

Whatever tool you use, you control the same four things.

First, what the agent knows. That is your prompt, a spec file, and repository instruction files such as CLAUDE.md and AGENTS.md. Second, what it can do. That is its tools, its permissions, its sandbox, and which branch it may push to.

Third, how it knows it is done. Tests, type checks, builds, screenshots or a reviewer. Fourth, how long it runs and how much it spends, set with turn limits, spend limits and time limits.

Lesson 09 covered the first. Lessons 08 and 14 cover the second, lesson 11 the third, and lesson 15 the fourth. This lesson is about using all four in a working day.

The autonomy spectrum

Each level of autonomy moves your check further from the edit

"Using AI to code" covers very different amounts of delegation. Six levels cover it, from autocomplete to a pipeline where no human reads the code.

"Using AI to code" covers very different amounts of delegation. This table names six levels.

Read the right-hand column, which says who checks each change. At autocomplete, you check as you type. In chat, you check line by line as you paste. With one supervised agent in your repo, you check each step or each diff. With several agents in parallel, you check each branch before it merges. With background agents, you or a reviewer check at the pull request, some time later.

At level six, specs go in and software comes out. No human reads the code, so automated checks are all that stand between the agent and production. People call these software factories or dark factories, after lights-out factories that run without people.

Dan Shapiro drew a similar map in January 2026 using self-driving cars. His top levels are a Waymo with a safety driver, a robotaxi, and the dark factory.

Yegge's eight stages

Move up one stage at a time, and down when the task calls for it

Yegge assumes permissions off from stage 3 up. Sandboxes, deny rules and worktrees get you most of the speed without that exposure.

Many experienced engineers switch stages by task: stage 6 for a batch of independent chores, stage 4 for a delicate change to payment code.

The list on screen is what to have in place at each stage. Each row replaces something you used to watch by hand.

At stage two you approve every command. When you catch yourself approving the same safe ones without reading, allowlist those, and only those. At stage three, Yegge turns permissions off. A sandbox, plus hard deny rules for secrets, pushes and production, gets you most of that speed. Lesson 14 covers how.

From stage four, tests are the contract and you ask for command output. From stage five, review moves from every edit to every pull request, and you never skip it. Stage six needs one worktree per agent and a written task list.

You are allowed to move down. Many experienced engineers pick the stage by task. A batch of independent chores can run at stage six. A delicate change to payment code goes back to stage four.

Explore, plan, implement, verify, commit

Anthropic's and OpenAI's docs recommend close to the same workflow. If the task is complex or hard to describe, have the agent plan before it codes.

Then give it a check to run, and have someone who didn't write the code review it.

"Codex can do this loop for you, but only if it knows what 'good' looks like."OpenAI, Codex best practices

Anthropic and OpenAI recommend close to the same workflow. Anthropic's April 2025 post on Claude Code called it explore, plan, code, commit, with a test-driven variant.

Here are the five steps. Explore read-only, so the agent builds a picture before it touches anything. Plan, and read the plan, because that is the cheapest place to catch a wrong idea. Implement with a failing test first. Verify by asking for evidence. Commit in small pieces, with the test and the fix in separate commits.

The quote under the steps is from OpenAI's Codex guide. The agent can run this loop for you, but only if it knows what good looks like. That is the runnable check from earlier in this lesson.

Anthropic's current docs stress the same points. Write a spec, give the agent a check to run, and have someone who did not write the code review it. The next two screens walk one bug through all five steps.

Implement and verify

Ask for the failing test first, then the passing output

A test that fails before the fix and passes after it is the contract the agent works to. Tell it not to modify the test.

"All tests pass" on its own "tells you very little", in Anthropic's words. Ask for the command and what it printed, then get a review from a fresh session.

Prototype first

When you don't know what you want, build a draft to find out

A throwaway version used to cost weeks, so teams argued over specs. An agent can build one in minutes, and you react to it.

A prototype looks finished. People start treating it as the real thing before anyone has checked error handling, security or tests.

Go deeper: prototype first

"Plan to throw one away; you will, anyhow."Fred Brooks, The Mythical Man-Month, 1975

1Timebox it and call it a draft. A spike/ branch or a scratch folder.
2Write what you learned into a short spec. Decisions, surprises, what users said.
3Rebuild or harden it on purpose. Start fresh with the core loop, or review the prototype line by line as production code.

Bryan's takeI like draft-driven or prototype-driven development, and you can do it with AI now. From a coding point of view or an application point of view, it's easier to comment on something you can see than to conceptualize it from scratch.

The core loop assumes you know what you want. When you don't, build a prototype to find out.

The idea is old. Fred Brooks wrote in 1975, plan to throw one away, you will anyhow. What changed is the price. A throwaway version used to cost weeks, so teams argued over specs. Now an agent builds one in minutes and you react to something real.

You can do it at two levels. For an application, put a clickable mockup in front of the people who will use it. For code, run a spike. Try two shapes of an API, read the real code, and pick one.

The risk comes from the same place as the benefit. A prototype looks finished. So follow the three steps on screen. Timebox it and say out loud that it is a draft. Write down what you learned. Then rebuild it or harden it on purpose. Brooks himself later called throw-one-away too simple and argued for growing software in increments.

A git worktree is another checkout of the same repository in another folder, on its own branch. Agents can edit at once without overwriting each other's files.

Pick tasks that touch different files, keep a written task list, and review every branch before merging.

Illustrative

A git worktree is another checkout of the same repository, in another folder, on its own branch. Every worktree shares one git history. That is how several agents can edit at once without overwriting each other's files.

The command at the top creates one. OpenAI's guide lists running live tasks on the same files without worktrees as a common mistake. Claude Code can create worktrees itself. As of November 2026 its batch command splits a large mechanical change into 5 to 30 units, each with its own worktree and pull request.

The rule is one task, one agent, one worktree, one branch. Pick tasks that touch different files. Two agents editing the same module give you a merge conflict, or worse, two inconsistent designs.

Keep a written task list that you and the agents can see. Review every branch before merging, because parallel agents multiply unreviewed code as fast as they multiply output. And watch the disk and the bill. Each worktree needs its own dependencies, and each agent spends tokens.

Most of the risk comes in when "I watch" becomes "I come back later". Anthropic's docs list five questions to answer before any unattended run.

One, does the agent know what done looks like. That can be a goal, a spec file, or a failing test to turn green. Two, can it check its own work. Tests, a review step, or a Stop hook, which blocks the agent from finishing until a check passes. Three, what is it allowed to touch. Permissions, a sandbox, a worktree, and one branch it may push to.

Four, what stops it. A turn limit or a spend limit. Five, where does the result go and who signs off. Usually a pull request, then a person approving the merge.

The simplest unattended run is a shell loop that hands the agent one file at a time, with a short list of allowed tools and a turn cap. The docs' advice for that loop is to try it on three files first, see what goes wrong, fix the prompt, then run the rest.

In February 2026, Nicholas Carlini of Anthropic described 16 parallel Claude agents building a C compiler in Rust from scratch. It took nearly 2,000 sessions, about two weeks, and just under 20,000 dollars. The result is roughly 100,000 lines that compile the Linux kernel, along with SQLite, PostgreSQL and Doom. StrongDM's AI team published a charter with two rules. No human writes the code, and no human reviews it. Correctness comes from end-to-end scenarios kept outside the codebase, and from behavioral clones of the third-party services they depend on.

Behind all of this is the trend from lesson 07. METR measures the length of task a model can finish with 50 percent reliability. That length doubled roughly every seven months from 2019 to 2025, and faster since.

The productivity evidence is mixed and still moving. In early 2025, METR ran a randomized controlled trial. Sixteen experienced open-source developers did 246 real tasks in their own repositories, some with AI tools allowed and some without.

Look at the top three bars. Before starting, the developers expected AI to make them 24 percent faster. Afterward, they believed it had made them 20 percent faster. The measured result runs the other way. With AI allowed, tasks took 19 percent longer.

METR now labels those results out of date. The hatched bar is its February 2026 follow-up. It estimated modest speedups, about 4 to 18 percent depending on the group, with confidence intervals that include zero. METR thinks that understates the real effect, because more and more developers refused to join a study that might make them work without AI.

So the felt speedup is bigger than the measured one, and the measured one is probably growing.

Ask why the gap between felt and measured speed might exist. Then ask how the room would measure its own team's real speedup.

The case against

The successes come with asterisks

The authors list the limits themselves. Carlini writes that "the thought of programmers deploying software they've never personally verified is a real concern."

Agents also cheat when they can. A pipeline that grades itself with tests the agent can see is grading on the honor system.

And agents cheat when they can. Frontier models have rewritten timers, patched evaluators and exposed hidden tests to post a passing score. Telling them not to often does not stop it.

Ask: if the rule is that no human reviews the code, who is accountable when it ships a security bug?

Until that spec is written down as checks an agent cannot game, full autonomy means shipping whatever passes the tests you happened to write.
