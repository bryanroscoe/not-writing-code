This lesson is about what agent work costs and how you pay for it. You will see where the tokens go, what a bill is made of, and when a flat subscription beats paying per token.

The two numbers on screen are the same hour of work with a coding agent. The first is without prompt caching and the second is with it. We will build that calculation step by step.

Three ways to pay

Subscribe to a lab or a tool vendor, or pay per token

A chat subscription and a tool subscription are flat monthly fees with usage caps. An API key bills you per token for exactly what you use.

Prices on these screens were checked on November 18, 2026. They change often, so learn the method and look up the numbers.

There are three ways to pay for a model. The first is a subscription to a lab, such as a Claude plan or a ChatGPT plan. You pay a flat monthly fee, roughly 20 to 200 dollars with one tier at 500, and you get the chat app plus the lab's own coding agent.

The second is a subscription to a tool vendor such as Cursor or GitHub Copilot. The vendor buys model access from the labs and resells it inside its product. The fee includes an allowance, and past that you pay as you go.

The third is an API key. You pay per token for exactly what you use. You can run any harness, build your own tools, run in CI and ship features to customers.

Every price in this lesson was checked on November 18, 2026. Prices move month to month, so keep the cost model and look up the numbers when you budget.

Ask the room who pays for their agent today and which of the three it is.

The token bill

An API bill has four lines that count

Input is everything you send. Output is everything the model writes, and it usually costs four to six times as much per token.

The two cache lines are how agent work gets affordable. Storing a prompt prefix costs a little extra, and reusing it costs a small fraction of the input price.

API prices are quoted per million tokens. A bill has four lines you need to know. The screen shows them for Claude Opus 5.5, a frontier model, as of November 2026.

Input is everything you send on a call: the system prompt, the tool definitions, the conversation history, files and tool results. It costs 4 dollars per million. Output is everything the model writes, and it costs 20 dollars. Output costs more to serve because each output token takes its own pass through the model, while input tokens are processed in parallel.

The last two lines are prompt caching. Writing a prefix into the cache costs a quarter more than plain input. Reading it back costs 20 cents per million, which is one twentieth of the input price.

One trap when you compare vendors. The same text becomes a different number of tokens on different tokenizers. A lower price per token on a tokenizer that produces more tokens can cost the same.

Ask which line they expect to dominate an agent's bill. Most people say output. Hold the answer until the worked example.

The token bill

Thinking tokens bill as output

A reasoning model that thinks for 5,000 tokens and then writes a 300-token answer bills you for 5,300 output tokens.

So the effort or thinking-budget setting changes your cost directly, at the most expensive rate on the bill.

Lesson 01 covered thinking tokens: text a reasoning model writes for itself before the answer. On the bill, those tokens are output.

The screen shows one reply. You read a 300 token answer. The model wrote 5,000 thinking tokens first, so you pay for 5,300 output tokens. At 20 dollars per million, the answer alone is about half a cent. With the thinking it is about ten and a half cents.

That is one call. An agent makes dozens of calls an hour, and it thinks on every one. The effort setting in your harness is a price setting too.

More thinking is not always more expensive overall. It often means fewer turns. Try the same task at two effort levels and compare the total cost of each run.

Watch for the belief that hidden thinking is free because you can't see it. You pay for all of it.

Why agents eat tokens

Every call sends the whole history again

The model needs the conversation so far on each call. In a simple agent loop, every tool result goes back along with everything before it.

The first call here sends 20,000 tokens. Each call adds 2,500. By call 60 the agent is sending 167,500 tokens to get one more step.

Why agents eat tokens

Input tokens grow with the square of the session

Each call is bigger than the last, so the total climbs faster than the call count. If every turn adds a fixed amount, total input grows roughly with the number of turns squared.

Doubling the calls more than triples total input here. As sessions get longer, that multiplier approaches four.

For your own work, this means one long session costs much more than two short ones covering the same ground. Start a fresh session when the task changes. Compact when the harness offers it. Keep big tool outputs out of the context.

Ask the room: why does doubling a session more than double its cost? Answer: every later call re-sends everything earlier, so the total is an area.

Prompt caching

Caching cuts the price of repeated input

Each call's prompt starts with the previous call's exact text. The provider can keep the processed state of that prefix and charge a small fraction of the input price to reuse it.

Claude Code and Codex do this for you. If you build your own agent on the API, put the stable parts of the prompt first.

Prompt caching is what makes that growth affordable. Each call's prompt begins with the exact text of the call before it. Only the end is new. The provider can keep the processed state of the repeated part and charge much less to reuse it.

The screen shows call 31 of our session. It sends 95,000 input tokens. Without caching, all of them bill at the full input price, which comes to 38 cents. With caching, 92,500 of them were already seen on the last call, so they bill as cache reads. Only the 2,500 new tokens are written. The call costs about 3 cents.

Harnesses such as Claude Code and Codex handle this automatically. If you build your own agent on the API, it is your job. Put the stable content first. On Anthropic's API you also mark cache breakpoints or turn on automatic caching.

Watch for the idea that caching returns a saved answer. The model still runs and writes a fresh reply. Only the repeated input is cheaper.

Now price an hour. The agent makes 60 calls, about one a minute. The first sends 20,000 tokens. Each call adds 2,500 to the context and writes 1,500 output tokens, thinking included. Nothing gets compacted, and you never step away for more than five minutes.

Put prices on those counts, using the frontier prices from earlier. Without caching, 5.6 million input tokens at 4 dollars per million is 22 dollars 50. Output is 1 dollar 80. The hour costs 24 dollars 30.

With caching, split the input in two. Every token is written to the cache once, the first time it appears. That is 167,500 tokens, or 84 cents. Every other time it is a cache read. That is about 5.5 million tokens at 20 cents per million, or 1 dollar 9. Output is unchanged. The hour costs 3 dollars 73, which is 85 percent less.

Output is now the largest line at 1 dollar 80, almost half the bill. A wordy model, or one set to think hard on every call, costs more than its price list suggests.

When you compare models for agent work, read the cache read price first. Most of your input tokens are billed at that rate.

Go back to the earlier question about which line dominates. Without caching it is input. With caching it is output.

Cache misses

A coffee break can cost 75 cents

Anthropic's default cache lasts five minutes. Step away longer and the next call writes the whole prefix again at the write price.

Caches match from the start of the prompt, so one change near the top throws away everything after it.

A cache entry expires. Anthropic's default lifetime is five minutes, refreshed each time the prefix is read. If you step away for six minutes, the entry is gone, and the next call has to write the whole prefix again.

The screen prices that for a 150,000 token context. Inside five minutes, the next call reads the prefix for about 3 cents. After the break it writes it again for 75 cents. Harnesses can ask for a one hour cache instead. That costs twice the input price to write.

The cache matches from the very start of the prompt. Change anything early and everything after it misses. A timestamp in the system prompt does it. So does a tool list that comes back in a different order, or switching settings in the middle of a session.

If you build an agent, order the prompt from most stable to least: tools, then system instructions, then project docs, then the conversation.

Ask who has put the current time in a system prompt. That one line makes every call a cache miss.

Model routing

Route easy work to a small model

Small models cost 20 to 100 times less per token than the bigger ones. Many harnesses let you set a different model for subagents.

Give the small model the rote work and keep the frontier model for planning, hard debugging and review.

Model routing means sending each piece of work to the cheapest model that can do it well. On screen are a small model and a frontier model from the same vendor, at November 2026 prices. On prompts up to 100,000 tokens, the frontier model costs 40 times as much per token.

The small model gets the rote work: renames, boilerplate, summarizing a log, classifying issues. The frontier model gets planning, hard debugging and review. Many harnesses let you choose a different model for subagents, which is the easiest place to start.

A small model that flails costs more than it saves. Route by how well specified the task is.

There are also flat-rate coding plans from labs that release open-weight models. One starts at 18 dollars a month and plugs into the popular harnesses. For many tasks they cost much less per unit of work. They usually trail the frontier on the hardest coding, and your code goes to a different provider in a different jurisdiction, so read the data terms.

API billing

Use the API for services, automation and batch jobs

Subscriptions fit your own interactive work. Anything that serves other people or runs unattended belongs on metered API keys, where usage can be attributed and limited.

A metered bill has no ceiling unless you set one. Put the controls in on day one.

Go deeper: when API billing is the right choice

Belongs on the API

  • Your own model-backed production service
  • CI and automation: review bots, issue triage, nightly jobs
  • Batch jobs that can wait a few hours, at 50% off
  • Multi-user apps
  • Work that needs zero data retention

Controls on day one

  • Spend limits that stop requests. An alert doesn't cap spending.
  • A separate key per app, environment and team
  • Caching on, stable content first
  • A cap on output tokens, thinking and turns per run
  • Tool outputs trimmed before they enter the context
  • A weekly cost review for the first month

Some work belongs on the API whatever the price comparison says. Your own production service is the clear case. CI and automation, such as review bots and nightly jobs, default to API keys too. Apps with many users need each user's usage to be attributed and limited.

Batch jobs get a discount. Anthropic, OpenAI and Google all take half off for requests that can finish within hours. Migrations, labeling and evaluation runs fit that well. Commercial API terms also default to no training on your data, and zero data retention is only available on commercial terms.

Check which of your provider's settings stop requests and which only send an email. An alert does not cap anything.

Use separate keys so you can see who spent what. Cap output tokens, thinking and the number of turns per agent run. Review the cost weekly for the first month of any new workflow.

Ask what would happen tonight if one of their agents looped until morning. Is there a hard stop?

Assume benefits, taxes and overhead bring the loaded cost to 1.4 times that, about 190,000 dollars. Divide by 1,800 productive hours and one engineer-hour is about 105 dollars. Round it to 100.

A 200 dollar seat then costs about two engineer-hours a month. A 20 dollar seat costs about twelve minutes. The heavy API user from the worked example costs about six hours.

That makes the cost side look easy. The gain is harder to prove. In the METR study from Lesson 07, experienced open-source developers using early-2025 tools took 19 percent longer on their tasks. They believed they were 20 percent faster. Tools have changed a lot since then, but self-reports still need checking.

Measure things you can count, before and after: cycle time, review turnaround, escaped defects and rework. Get the vendor's data terms in writing before a rollout.

Ask what they would measure to decide whether a 200 dollar seat is paying for itself.

What to remember

Three things to keep

  • Without compaction, agent input grows roughly with the square of the session. Caching, shorter sessions and trimmed tool output keep the bill down.
  • Subscriptions fit your own interactive work until you hit the cap. Use the API for services, automation and batch.
  • Judge cost per finished task, and measure your own usage before you budget.
