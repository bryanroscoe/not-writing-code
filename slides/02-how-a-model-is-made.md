# 02: How a model is made

Data, compute, hardware, and pretraining

## Why this matters

- Every model you use was made in stages

## From the library to a base model

## The pipeline at a glance

pretraining → mid-training → **base model** → supervised fine-tuning → preference tuning → reasoning RL → agentic RL → general RL → safety training → **released model**

Afterward, optionally: your own fine-tune (open weights), or distilled smaller models.

Real pipelines repeat, overlap, and run stages in different orders.

<!--
The analogy is an education: read the entire library (pretraining), study the best books closely (mid-training), apprentice with worked examples (supervised fine-tuning), get coached on what people prefer (preference tuning), drill practice exams that have an answer key (RL), take a professional-conduct course (safety training), and then, optionally, do a specialty residency (your fine-tune).

Treat it as a mental model. Recent open recipes run several RL stages, not one. GLM-5 runs "Reasoning RL, followed by Agentic RL, and finishing with General RL," with on-policy distillation between stages. DeepSeek-R1 alternated RL and supervised fine-tuning, and DeepSeek-V4 trains separate RL specialists and then merges them into one model.

Everything after the base model is post-training: supervised fine-tuning on example conversations, preference tuning on pairs of better and worse responses, and several rounds of reinforcement learning on tasks a program can check. That's module 03. Today stops at the base model, then picks up distillation at the end.
-->

## Pretraining: reading the library

| Model | Pretraining tokens |
| --- | --- |
| Llama 3 (Meta, 2024) | More than 15 trillion |
| DeepSeek-V3 (2024) | 14.8 trillion |
| Qwen3 (Alibaba, 2025) | About 36 trillion |

Next-token prediction over filtered web crawls, code, books, papers, and synthetic data. Closed labs mostly don't publish these numbers.

<!--
The goal is a base model that predicts the next token well across almost everything people write (module 01).

Most of the data comes from web crawls such as Common Crawl, filtered hard: duplicates, spam, and boilerplate come out, classifiers score quality, and some personal data gets stripped. Hugging Face's open FineWeb project documents the process; it got about 15 trillion tokens out of Common Crawl. Labs add code from public repositories, books, scientific papers, math, many languages, and more and more synthetic data generated by other models. Data quality matters as much as quantity. Training data is also the subject of copyright lawsuits and consent debates (module 18).

The output is a base model. It completes documents but doesn't yet follow instructions reliably or refuse harmful requests.

Mid-training is a loose name for a phase between bulk pretraining and post-training, and labs use it differently. It usually means higher-quality, specialized data (math, code, reasoning traces, long documents), stretching the context window, and slowly lowering the learning rate while training on the best data. It's late pretraining focused on quality and specific skills.
-->

## What a training run costs

| Scale | Rough compute cost | Example |
| --- | --- | --- |
| Teaching toy | About $100 | Karpathy's nanochat: about 4 hours on one 8-GPU node |
| Small open model (~8B) | A few million dollars | Llama 3 and 3.1 8B: ~1.3–1.5 million H100 GPU-hours |
| Large efficient open model | About $5–6 million, final run | DeepSeek-V3: 2.788 million H800 GPU-hours |
| Frontier closed model | Hundreds of millions, rising | Largest runs projected past $1 billion by 2027 |

The headline number for one run understates the real bill.

<!--

The real bill includes years of experiments, data work, and people.

# Part 2

## The hardware

<!--

-->

---

## A model is mostly matrix multiplies

- One FLOP is one floating-point multiply or add
- Forward pass: about 2 FLOPs per parameter per token
- Training adds a backward pass: about **6 FLOPs per parameter per token**
- A GPU has thousands of simple cores plus matrix units (Tensor Cores)
- H100: about 67 TFLOPS of FP32, 989 TFLOPS of dense BF16 matrix math

<!--
A transformer layer is mostly matrix multiplication: token vectors times large weight matrices, over and over (module 01). A forward pass costs one multiply and one add per parameter per token. The backward pass costs about twice that, so training costs about 6 FLOPs per parameter per token (Kaplan et al., 2020). That's where module 01's 6·N·D rule comes from.

A CPU has a few dozen powerful cores built for branchy, unpredictable code. A GPU makes the opposite bet. Google's TPUs, AWS's Trainium and AMD's Instinct chips make the same bet; together they're called accelerators.

Read spec sheets carefully. NVIDIA's headline numbers usually assume 2:4 sparsity, which doubles them, so the H100's 1,979 BF16 TFLOPS is 989 dense.
-->

---

## Arithmetic intensity: FLOPs per byte moved

| 16-bit numbers | Work | Data moved | FLOPs per byte |
| --- | --- | --- | --- |
| 4,096 × 4,096 matrix times matrix | ≈137 billion FLOPs | ≈100 MB | ≈1,400 |
| Same matrix times one vector | ≈34 million FLOPs | ≈34 MB | ≈1 |

The second row is what a model does when it writes text for one user.

<!--
A chip can only compute on numbers it has fetched from memory, and fetching takes time. Arithmetic intensity tells you which one limits you.

First row: the work is 2 × 4,096³. The data is two matrices in and one out, 3 × 4,096² × 2 bytes. Every number fetched gets used thousands of times.

Second row: the work is 2 × 4,096². The matrix alone is 4,096² × 2 bytes. Every weight is fetched, used once, and dropped.

Similar math, very different behavior on the chip.
-->

---

## The memory wall

Every two years in server hardware (Gholami et al., 2024):

| Peak FLOPs | DRAM bandwidth | Interconnect bandwidth |
| --- | --- | --- |
| ×3.0 | ×1.6 | ×1.4 |

H100: 989 TFLOPS ÷ 3.35 TB/s ≈ **295 FLOPs per byte**. Below that, you wait on memory. Above it, you wait on math.

<!--
Chips have gained compute much faster than memory bandwidth. The widening gap is called the memory wall.

The H100 ratio is the crossover point. The roofline model draws this as a sloped bandwidth line meeting a flat compute ceiling (Austin et al., How to Scale Your Model).

The ratio has barely moved on newer chips. From vendor specs, BF16 FLOPs per byte is about 280 for NVIDIA's B200, 210 for Rubin, 215 for AMD's MI455X, and 310 for Google's Ironwood. To place any new chip, divide its FLOPs by its bandwidth.
-->

---

## One user, one H100, Llama 3 8B

Weights in BF16: 16 GB, all read once for every new token.

| If the limit were… | Time per token | Tokens per second |
| --- | --- | --- |
| Memory: 16 GB at 3.35 TB/s | ≈4.8 ms | ≈210 |
| Math: 16 billion FLOPs at 989 TFLOPS | ≈16 µs | ≈60,000 |

Going by peak specs, the chip spends more than 99% of the time waiting on memory.

<!--
This is the memory wall from the user's side. Going by those peak specs, one sequence tops out near 210 tokens per second. That's a bound set by bandwidth, not a measured speed. Module 06 uses the same bound to estimate speed on a laptop.

The fix is batching. Serve B users at once and each weight fetched gets used B times, so intensity rises to about B FLOPs per byte. On an H100 you'd need a batch of roughly 300 before decoding stops being bandwidth-bound. Each user's KV cache is separate, so those reads don't get shared. That's why serving at scale is mostly a batching and memory-management problem.
-->

---

## Training and inference hit different limits

| | Training | Inference |
| --- | --- | --- |
| Usually bound by | Compute | Memory bandwidth (decode) |
| Why | Huge batches: 16 million tokens per step for Llama 3 405B | One sequence on a dense model: each token rereads every weight |
| Memory problem | Capacity: ~16 bytes per parameter, ~6.5 TB for 405B | Weights plus KV caches |

Prefill reads your prompt at once, like training. Decode writes one token at a time.

<!--
Accelerators keep weights in HBM, high-bandwidth memory: stacks of DRAM chips mounted in the same package as the processor, wired with a very wide bus. An H100 has 80 GB of HBM3 at 3.35 TB/s. AMD's MI455X has 432 GB across 12 HBM4 stacks at 23.3 TB/s. Bandwidth bounds decode speed. Capacity bounds what fits.

Training reuses each weight across millions of tokens, so the math units stay busy. The measure is MFU, model FLOPs utilization: the share of the chip's peak FLOPs spent on the model's own math. Llama 3 reached 38–43% MFU in BF16.

Training's memory problem is capacity. Mixed-precision training with Adam keeps 16-bit weights and gradients, a 32-bit copy of the weights, and two 32-bit optimizer values. For 405B that's at least 81 H100s just to hold it.

Prefill is compute-heavy; decode is the bandwidth-bound case. Running both on the same GPUs makes them interfere. DistServe served up to 7.4× more requests by splitting them onto separate GPUs (Zhong et al., 2024).
-->

## Fewer bits per number

| Format | Bits | Where it fits |
| --- | --- | --- |
| FP32 | 32 | The old default |
| BF16 | 16 | FP32's range, less precision; usual for training and released weights |
| FP8 | 8 | Matched 16-bit quality up to 175B; DeepSeek-V3 trained in it |
| MXFP4, NVFP4 | 4 | Small blocks share a scale factor (32 values; 16 values) |

Fewer bits: less memory, fewer bytes per token, more math per second.

<!--
Mixed-precision training (2017) moved most of the work to 16 bits and kept a 32-bit copy of the weights, nearly halving memory. FP8 comes in two encodings, E4M3 and E5M2, one favoring precision and one favoring range.

FP4 has only 16 possible bit patterns, so it needs help. MXFP4 comes from an industry spec written by AMD, Arm, Intel, Meta, Microsoft, NVIDIA and Qualcomm, with a power-of-two scale per block of 32. NVIDIA's NVFP4 uses blocks of 16 with an FP8 scale, about 4.5 bits per value in all.

Chips are moving this way. Rubin's dense NVFP4 training rate is about 9× its BF16 rate, and Blackwell Ultra gave up most of its INT8 and FP64 throughput for more FP4. Google built native FP4 into TPU 8t "to overcome memory bandwidth bottlenecks." gpt-oss was post-trained with its MoE weights in MXFP4, which lets the 120B model run on one 80 GB GPU. Lower precision costs some quality; quantization, at the end of this deck, covers that trade.
-->

## Why one model needs thousands of chips

Llama 3 405B on one H100: about 3,000 years, and 6.5 TB of training state.

| Tier | What it links | Example |
| --- | --- | --- |
| Scale-up | A small group that can read each other's memory | NVLink, TPU ICI; 1.8 TB/s per GPU in an HGX B300 |
| Scale-out | The datacenter network between groups | InfiniBand or Ethernet; that server gets 1.6 TB/s total |

About 9× less bandwidth per GPU once you leave the server.

<!--
The work gets split across thousands of chips that talk constantly, over two tiers of wiring.

Scale-up examples: NVIDIA's NVL72 racks put 72 GPUs in one NVLink domain. Google's Ironwood pods link up to 9,216 TPUs. Scale-out example: Meta's Llama 3 cluster used 400 Gbps Ethernet (RoCE) across 24,000 GPUs, eight per server on NVLink.

That gap shapes the software. DeepSeek's H800s, an H100 variant with cut-down NVLink sold in China under U.S. export rules, got 160 GB/s over NVLink and 50 GB/s over InfiniBand, so DeepSeek limited how many servers each token's experts could span.
-->

---

## Four ways to split the work

| Parallelism | What gets split | Note |
| --- | --- | --- |
| Data | The batch; gradients averaged each step | ZeRO and FSDP shard the state too |
| Tensor | Individual weight matrices | Needs the fastest links; stays in one NVLink domain |
| Pipeline | Consecutive groups of layers | Micro-batches stream through like an assembly line |
| Expert | A mixture-of-experts model's experts | Tokens sent to their experts, all-to-all |

Put the most talkative split on the fastest wire.

<!--
Real runs combine them. Llama 3 405B used tensor parallelism across the 8 GPUs of a server, 16 pipeline stages, and data parallelism up to 128 ways.

Sources, if anyone asks: ZeRO (Rajbhandari et al., 2019), Megatron-LM for tensor parallelism (Shoeybi et al., 2019), GPipe for pipeline parallelism (Huang et al., 2018), and GShard for expert parallelism (Lepikhin et al., 2020).
-->

## Worked example: Llama 3 405B

| Step | Arithmetic | Result |
| --- | --- | --- |
| 1. FLOPs | 6 × 405×10⁹ params × 15.6×10¹² tokens | ≈3.8×10²⁵ (paper: 3.8×10²⁵) |
| 2. GPU-hours | ÷ ~400 TFLOPS measured per H100 | ≈26 million |
| 3. Days | Spread over 16,384 H100s | ≈1,600 hours, 67 days |
| 4. Check | Llama 3.1 405B model card | 30.84 million H100-hours, ~17% more |

<!--
Meta published enough to check each step.

For step 2, use Meta's measured 400 TFLOPS per H100. The spec sheet's 989 TFLOPS would overestimate the throughput. 3.8×10²⁵ ÷ 4×10¹⁴ FLOPs per second is about 9.5×10¹⁰ GPU-seconds, about 26 million GPU-hours.

Step 3: that's 67 days of pure compute. On one GPU it would take about 3,000 years.

Step 4: the card doesn't say where the extra 17% went.
-->

## At this scale, hardware fails all the time

In a 54-day stretch of the 405B run:

- 466 job interruptions: 47 planned, 419 unexpected
- About one every three hours
- Roughly 78% of the unexpected ones: confirmed or suspected hardware
- Only three needed significant manual work
- Effective training time stayed above 90%

<!--
GPU issues alone were 58.7% of the unexpected interruptions. Automation handled nearly all of them.

Throughput also varied 1–2% with the time of day, because heat made the GPUs lower their clock speeds.

The Llama 3 paper's sections 3.3 and 6 are a first-hand account of a 16,000-GPU run, including the network, parallelism, failures and power swings. Worth reading if this part grabbed you.
-->

## DeepSeek-V3's GPU-hours, with the paper's caveats

2.788 million H800 GPU-hours ≈ $5.576 million at $2 per GPU-hour.

- Excludes "prior research and ablation experiments"
- A rental price, not the cost of owning 2,048 GPUs
- Builds on R1, whose compute isn't in the total
- An MoE: 671B parameters, 37B active per token

6 × 37×10⁹ × 14.8×10¹² ≈ 3.3×10²⁴ FLOPs, about 11.5× less than Llama 3 405B.

<!--
The breakdown: 2.664 million hours of pretraining, 119,000 for context extension and 5,000 for post-training, on a 2,048-GPU cluster. Pretraining took less than two months.

The paper's own words: the costs "include only the official training of DeepSeek-V3, excluding the costs associated with prior research and ablation experiments on architectures, algorithms, or data."

Post-training distilled reasoning from DeepSeek's R1 series.

The GPU-hour ratio, 30.84M ÷ 2.788M ≈ 11×, is close to the FLOP ratio. The smaller workload explains most of the difference in GPU-hours. Discussion question 2 comes back to this.
-->

## Power: from one chip to the grid

| Unit | Power |
| --- | --- |
| One H100 | Up to 700 W |
| One AMD MI355X | 1,400 W |
| One Rubin GPU, with its share of the facility | About 2.5 kW |
| One gigawatt | Roughly 400,000 Rubin-class GPUs |

Llama 3.1 405B: about 21.6 GWh for the GPUs alone.

<!--
A datacenter also powers CPUs, networking and cooling. NVIDIA's Vera Rubin spec sheet plans for 40,000 GPUs per 100 MW, which is where 2.5 kW per GPU and the gigawatt rule of thumb come from.

The 21.6 GWh is 30.84 million H100-hours at 700 W. Big runs also strain the grid in a less obvious way. When tens of thousands of GPUs pause together, for example while saving a checkpoint, Meta saw power draw swing "on the order of tens of megawatts, stretching the limits of the power grid."

At grid scale, the IEA estimates data centers used about 415 TWh in 2024 (about 1.5% of the world's electricity) and 485 TWh in 2025, and projects about 950 TWh by 2030. LBNL, reporting for the U.S. Department of Energy, found U.S. data centers used 192 TWh in 2024, 4.7% of U.S. electricity, with a 2030 reference case of 649 TWh, or 11.8%.

One gigawatt running all year is 8.76 TWh, so a 5 GW campus at full load would use about 44 TWh a year, close to a quarter of all U.S. data center electricity in 2024. Announced capacity isn't average draw, so treat that as a ceiling.
-->

## Training chips vs inference chips

Google's TPU 8t and TPU 8i (announced April 2026):

| | TPU 8t (training) | TPU 8i (inference) |
| --- | --- | --- |
| FP4 compute | 12.6 PF | 10.1 PF |
| HBM | 216 GB | 288 GB |
| Bandwidth | 6.5 TB/s | 8.6 TB/s |
| On-chip SRAM | 128 MB | 384 MB |

<!--
Training wants low-precision FLOPs, memory for optimizer state, and fast links across thousands of chips working in lockstep for weeks or months. Inference wants memory bandwidth, memory capacity for weights and KV caches, and fast answers for each user. Vendors now build separate chips for each job, and this pair shows the split.

Serving a big model is its own engineering problem. Llama 3 405B in BF16 "does not fit in the GPU memory of a single machine with 8 Nvidia H100 GPUs," so Meta served it across 16 GPUs on two machines. Module 01 explains the KV cache, and module 06 walks through the memory math for running a model yourself.
-->

## Distillation: teacher → student

| Flavor | The student learns from | Where it happens |
| --- | --- | --- |
| Logit | The teacher's token probabilities | Inside a lab |
| Output | The teacher's generated text | Through any API that returns text |
| On-policy | The teacher grading every token of the student's own answers | Now a core post-training step |

On-policy distillation used about a tenth of RL's GPU-hours in one comparison (1,800 vs 17,920).

<!--
Distillation means training a smaller student model to imitate a larger teacher. Hinton, Vinyals, and Dean (2015) showed that the teacher's full probability distribution (it thinks "cat" 70%, "lynx" 20%, "dog" 5%) carries more information than the single right answer.

On-policy distillation lets the student learn from its own mistakes instead of copying the teacher's text. The comparison is from Thinking Machines. DeepSeek-V4 uses it to merge separately trained expert models into one, and GLM-5 uses it between RL stages so the model doesn't forget earlier skills. Module 03 covers the RL stages it connects.

Established uses: Stanford Alpaca (March 2023) fine-tuned LLaMA 7B on 52,000 instruction examples generated with OpenAI's text-davinci-003, for under $600 total. DeepSeek's R1-Distill models (January 2025) were Qwen and Llama models fine-tuned on R1's reasoning traces. Self-Instruct (2022) had a model write its own training instructions, and Microsoft's first Phi model trained on "textbook-quality" filtered web data plus synthetic textbooks from GPT-3.5. Labs generate math problems with checked answers, code with tests, and reasoning traces, keeping only the outputs that verify.

One risk: model collapse. Train each generation on the previous generation's outputs and rare information vanishes first, then outputs converge on bland averages (Shumailov et al., Nature 2024). Keeping real data alongside synthetic data avoided it in follow-up experiments.
-->

---

## The distillation fight

- Closed labs' terms forbid using outputs to build competing models
- Feb 12, 2026: OpenAI told a House committee DeepSeek used distillation to "free-ride"
- Feb 23, 2026: Anthropic reported 16M+ exchanges via ~24,000 fraudulent accounts
- June 2026: Fable 5 sends flagged distillation attempts to Opus 4.8
- Oct 12, 2026: Anthropic claims new defenses cut harvested data 90–99%

<!--
Anthropic named DeepSeek, Moonshot, and MiniMax: DeepSeek more than 150,000 exchanges, Moonshot more than 3.4 million, MiniMax more than 13 million. It called distillation "a widely used and legitimate training method" in general and objected to its illicit use. Earlier, in August 2025, Anthropic cut off OpenAI's access to Claude, saying OpenAI's use violated terms against building competing products; OpenAI said it was benchmarking.

At Fable 5's launch on June 9, 2026, Anthropic said users would be told when that rerouting happens. Within days, after reporting that one safeguard aimed at frontier-model development had been changing answers without telling users, Anthropic apologized and said it would make that safeguard visible.

The October defenses: a classifier Anthropic says has a false-positive rate under 0.1%, limits on editing Claude's earlier reasoning for new API accounts, and stricter limits for repeat offenders.

There's another side. Critics point out that frontier labs trained on web content without asking permission, which makes complaints about copying sound selective. Outsiders can't verify the account-level evidence. And the accusations land in a policy fight over export controls, where every party has an interest. Distilling a strong model works, and frontier labs now actively defend against it. Those defenses sometimes affect legitimate users.
-->

## Quantization basics

| Precision | Bytes per parameter | 8B model weights | Typical quality |
| --- | --- | --- | --- |
| 16-bit (bf16/fp16) | 2 | ~16 GB | Reference |
| 8-bit | 1 | ~8 GB | Usually close to reference |
| 4-bit | ~0.5 | ~4.5–5 GB | Often a small loss; worse on small models, code, and math |

Re-run your evaluation after quantizing.

<!--
Quantization stores weights with fewer bits: less memory and usually faster inference, at some cost in quality. It's the low-precision idea from Part 2, applied to a finished model.

Common methods and formats:
- GPTQ (Frantar et al., 2022) quantizes layer by layer, adjusting remaining weights to compensate for rounding errors.
- AWQ (Lin et al., 2023) protects the small fraction of weights that matter most, judged by activation sizes.
- GGUF is the single-file format used by llama.cpp and tools built on it, such as Ollama and LM Studio. Files come in levels like Q4_K_M (about 4-bit) and Q8_0 (8-bit).
- MLX has its own quantized formats for Apple Silicon.

You can quantize a finished model to serve it cheaply, or quantize the base to train adapters cheaply. That second one is QLoRA, in module 03.
-->

## Try it

No GPU, no downloads:

1. **Memory math:** 3B, 8B and 70B models at 16-bit and 4-bit
2. **Read a model card:** base model, method, data, license, claims
3. **Estimate a training run:** 6·N·D, a chip, 40% of peak, GPU-hours, days
4. Then the memory wall for the same model: tokens per second, and the batch size that ends the bandwidth limit

<!--
1. Work out inference memory by hand and check it against the quantization table.
2. On Hugging Face, open a popular fine-tune of an open-weight model. Find the base model, the method (full, LoRA, DPO, merged), the training data, the license, and the evaluation claims. Write down what's missing. Then open a GGUF repository's Files tab and compare the sizes of Q4_K_M, Q8_0, and F16 files.
3. Pick an open model whose paper or card gives its parameter count and training tokens: Qwen3, DeepSeek-V3, or a Llama 3 size other than 405B. Compute 6·N·D, using active parameters for an MoE. Pick a chip from the table, assume 40% of its dense BF16 peak, and work out GPU-hours, then days on 2,048 and on 16,384 chips. If the card reports GPU-hours, compare and list what your estimate leaves out.
4. For the same model on the same chip: the most tokens per second one user could get, and the batch size where decoding stops being bandwidth-bound.
-->
